# C9b: the contradiction probe reads only the newest 1000 claims

Follow-up of C9 (same cap, different place). Checked against origin/main 5578d27.

## Problem
`probe_claim_contradictions_for_queries` (eval/contradictions.py:198-240) loads `list_claims(active=True, limit=1000)` once, builds
`by_memory_key` and `by_subject` indexes from that window, and then, for each query's recalled keys, selects the claims of those keys
plus every claim that shares a subject with them before running `detect_claim_contradictions`. In a project with more than 1000 active
claims, claims outside the newest 1000 are silently missing from both indexes: a recalled memory's older claim, or an older claim on
the same subject, never reaches the detector, so a real contradiction goes unreported and the report's counts are too low. No error is
raised. It is the same defect C9 fixed in the recall evidence path (stateplane.py `_recall_profile_evidence`); the probe was left out
because it also needs the by-subject claims, which no keyed read provided.

The probe is eval tooling: `bilinc.eval` is pruned from the wheel and sdist (MANIFEST.in `prune src/bilinc/eval`); it is exported from
`eval/__init__.py` and used in tests/test_eval_contradictions.py:127-168. No script or benchmark in the repository calls it.

How found: `grep -rn "list_claims(" src/bilinc`; the other unkeyed 1000-row read was `_recall_profile_evidence`, closed by C9; the
`limit=max(1000, len(wanted)*100)` fallback in `_active_claims_by_memory_key` only runs for a backend without the keyed method (none in the
tree).

## Approaches
1. Raise the limit. Still arbitrary and loads the whole claim table into Python for every probe.
2. Per query, read the recalled keys with the existing `list_claims_for_memory_keys`, then each subject with
   `list_claims(subject=..., limit=N)`. The second call has the same cap problem for a subject with many claims.
3. Add `list_claims_for_subjects(subjects, active=True)` to both backends (the counterpart of `list_claims_for_memory_keys`:
   same active/validity filters, `updated_at DESC`, no row cap, `IN (...)` on SQLite, `= ANY($1)` on Postgres) and have the probe read, per
   query, the recalled keys' claims and then the claims of their subjects, with a per-probe cache so a key or subject is read once.

Chosen: 3. The probe builds `selected` exactly as before (claims of the key, then the claims of the key's claims' subjects, in
newest-first order), so for projects at or below 1000 claims the report is identical; for larger ones it now sees what it was meant to.
With no recalled keys nothing is read. A backend without the two keyed methods keeps the old global read (none in the tree).

## Test plan (tests first, `bilinc-test`; SQLite always, Postgres gated on `BILINC_TEST_POSTGRES_DSN`)
- Backend method, both backends: `list_claims_for_subjects` returns only the given subjects, applies active/validity filters, orders newest
  first, returns more than 1000 rows when they exist (no cap), returns `[]` for an empty list without querying, and never returns another
  project's claims (Postgres tenant schemas; second project with the same subject).
- Probe, SQLite: two contradicting claims on subject S (one on a recalled memory, one on another memory of the same subject), then 1100
  newer claims on other subjects. On origin/main the contradiction is missed; with the fix it is found and counted, `queries_with_contradiction`
  is 1. Same on Postgres through a hosted plane (`ProjectRuntimeManager.get_plane`).
- Control: the existing probe test, and a small-project case, give an identical report (same findings, same order) before and after.
- No recalled keys: the backend is not asked for claims. A stub backend without the keyed methods keeps working through the old path.
  A backend error propagates.
- A key or subject shared by two queries is read once (stub backend counting calls).
- Mutation check: reverting the probe to the global `limit=1000` read fails the scenario tests; dropping the per-probe cache fails the call-count test.

## Release-chain impact
- PyPI package: none (`eval/`, `storage/` and `core/` are pruned from the wheel and sdist). SDK, hosted runtime, site, MCP registry:
  no change (the probe is eval tooling; nothing hosted calls it). Migration: none; rollback is a revert.
- Source-only API addition: `list_claims_for_subjects` on the SQLite and Postgres backends.
- CHANGELOG `[Unreleased]` entry in neutral wording. Version number is the owner's decision.
