# PREV-VAL: legacy `metadata.previous_value` keeps text of replaced values

## Problem
Before 2.6.0, a revision that replaced a value copied `repr(old value)[:200]` into the new entry's `metadata.previous_value` (`adaptive/agm_engine.py`; the fix is `b897427`). Since 2.6.0 a revision stores only `previous_value_sha256` and pops the old field (`agm_engine.py:474-478`). That fixes new revisions only. Rows written before the fix still hold up to 200 characters of an older value, and nothing in the code removes them (`grep previous_value src/` finds the one `pop`, and the sha256 line).

Why the text stays and spreads:
- A stored row is loaded into memory as a `MemoryEntry` with its metadata. Paths that rewrite the entry without replacing its value copy that metadata forward unchanged, so the text lands again in the row, the audit `before`/`after`, the event payload (`core/stateplane.py:3324, 3577`: `payload_json={"metadata": entry.metadata, ...}`) and the next snapshot file:
  - `confirm` (`cloud/runtime.py:898-935`): by design "metadata stays exactly as stored";
  - `revise` with an identical value (`runtime.py:985-1025`): AGM treats it as a no-op and the entry built from `previous_state` keeps the metadata;
  - a TTL rewrite and `consolidate` (`core/stateplane.py:1543-1560`), which saves the buffered entry as it is;
  - a rollback restore (`runtime.py:1442-1459`), which restores the snapshot's entries as they were.
- The local database of the owner holds 200 such rows (Vault Local-Audit "Data quality"); production is unknown.
- **Hosted routes** return no metadata (other than the diff listing keys), so there the leftover text is storage exposure. **The local MCP `diff` tool is a read route that does return it:** it returns `StatePlane.diff` as is (`mcp_server/server_v2.py:1668-1672`), and `StatePlane.diff` puts the raw audit `before`/`after` dicts, metadata included, into `added`, `removed` and `modified` (`core/stateplane.py:3071-3086`; the dicts come from `audit.get_state_at`, `core/audit.py:325`, `postgres_audit_sync.py:213-215`). So a legacy `previous_value` is readable through the local API today. The leftover text defeats "revise to remove sensitive text".

## Approaches
1. **Reserve the field name with one helper, applied at every place metadata enters an entry (chosen, for new copies).** A helper `strip_reserved_metadata(metadata)` in `core/models.py` returns the metadata without `previous_value` (a copy only when the key is present, so a caller's dict is never mutated). It is called:
   - in a new `MemoryEntry.__post_init__` (`MemoryEntry` has none today; the one at `core/models.py:85` belongs to the claim dataclass). It touches only `metadata` and does not reorder or change any other field, because `to_dict` equality drives the rollback and version checks. It covers every entry that is loaded from a backend, rebuilt from a snapshot (`from_dict`) or a request;
   - in `commit_with_agm_async` right after `entry.metadata.update(metadata)` (`core/stateplane.py:3493-3494`). That merge runs after construction, so `__post_init__` alone would miss a `previous_value` that a caller passes to a new key or to a non-replacing write, and the field would reach the row, event, audit entry and snapshot;
   - at the current-state projection that assigns `projection.metadata` after `copy(entry)` (`stateplane.py:1920-1926`), which also assigns outside the constructor.
   With this, the next write of any legacy row of any kind (confirm, same-value revise, TTL, consolidate, rollback) persists it clean, and the field never reaches events, audit or snapshots again. No migration, no schema change.
   - Cost: `previous_value` becomes a reserved metadata key. AGM already pops it on every replacing revision (`agm_engine.py:474-475`); this extends that rule to every write and load. The release note says so.
2. **Strip it only in `backend.save` / `restore`.** Catches the persisted row but not the in-memory entry that has already been used to build event payloads and audit values, so the event and audit copies would still carry it. Rejected.
3. **Scrub at rest only (a script).** Cleans what exists but does not stop a legacy row that has not been scrubbed from copying the text again on its next confirm or rewrite. Needed as well, for rows that nobody writes again (below), but not sufficient. Chosen as the second part, not alone.

**Local `diff` output.** Two options: (a) remove `previous_value` from the `before` and `after` entries that `StatePlane.diff` returns, with `strip_reserved_metadata` applied to each entry's `metadata`; the audit rows are not touched, so the chain stays valid; or (b) accept the readable text as a known residual. (a) is chosen: the fix is small, the owner's local agents call this tool, and (b) would leave an API that returns the text the change is meant to stop spreading. The comparison runs on the raw audit states, and a key whose cleaned `before` equals its cleaned `after` (the only change was the legacy field) is then dropped from `modified`, so the output never shows an identical pair. The `counts` follow the filtered lists. Other consumers of audit state dicts found by `grep get_state_at\|after_value src/` get the same treatment during the build, each with a test, or are listed in the ready note as a residual.

**Rollback preview, diff and restore.** The preview compares the snapshot's raw entry dicts (`_snapshot_entries`) with `plane._persistent_state()`, which builds `MemoryEntry` objects and so returns the cleaned state (`cloud/runtime.py:1419-1425`, `core/stateplane.py:330-334`). After this change, a legacy key in an old snapshot would show as `update` even when nothing else differs, which corrupts the count and the list an operator confirms before a destructive restore, and `rollback_execute` would rewrite those keys and add events and audit rows. The target state therefore goes through the same normalisation before the comparison: `plane._entry_to_state(MemoryEntry.from_dict(raw))` for each snapshot entry, in both `rollback_preview` and `rollback_execute`, so only keys that really differ are listed and rewritten. The same normalisation applies in two more places that compare a raw target with a cleaned current entry: the local `StatePlane.rollback`, which compares `existing.to_dict()` with the audit's raw `target_entry_dict` (`core/stateplane.py:3140-3143`; without it every legacy key is rewritten and gets a new audit row, and the local side is the reference behaviour), and the hosted `diff` (`cloud/runtime.py:1350-1369`), which would otherwise list legacy keys as `modified`. Both sides of every hosted diff mode are normalised, snapshot-to-snapshot included, so "A to current" and "A to a snapshot of current" agree. `MemoryEntry.from_dict` mutates its input (`core/models.py:143-144` replaces `memory_type`), so every call passes a copy, `dict(raw)`, and the loaded snapshot payload is never changed.

**At-rest scrub (second part).** `scripts/scrub_legacy_previous_value.py` removes the key from the `metadata` column of existing rows.
- Targets: Postgres tenant schemas (`bilinc_entries.metadata`, JSONB: `metadata - 'previous_value'`) and a SQLite database file (`memories.metadata`, text JSON: `json_remove(metadata, '$.previous_value')`, only for rows where `json_valid(metadata)`).
- Default is read-only: it counts the rows that carry the field and writes nothing. `--execute` updates them. Postgres uses a plain connection (no `init()`, the pattern of `scripts/prewarm_pg_tenants.py --dry-run`, which is on main; the sweep script of backlog item A4r follows the same pattern but is not a dependency); `--sqlite PATH` takes a file.
- `--execute` on a SQLite file refuses to run unless `--backup-dir` is given; it first copies the database with SQLite's online backup API (`sqlite3.Connection.backup`), verifies the copy opens and holds the same row count, then updates in one transaction that starts with `BEGIN IMMEDIATE`. If the database is busy (another Bilinc process holds it open for writing) the script changes nothing and exits non-zero with a message to try again with the other processes stopped. The copy is written with mode 0600 and holds the very text being removed, so the script prints that it is the owner's to keep or destroy once the result is verified. On Postgres the way back is the count-only run and the nightly off-site backup; the script says so and does not take a copy itself.
- **Physical removal.** The store's own purge removes text physically (`PRAGMA secure_delete=ON`, `sqlite.py:99`, and `wal_checkpoint(TRUNCATE)`, `sqlite.py:971`). The script does the same on the SQLite file: it sets `secure_delete=ON` before the update and runs `wal_checkpoint(TRUNCATE)` after it, so freed pages and the `-wal` file do not keep the 200 characters. On Postgres the removed text stays in dead tuples until vacuum, and the expression index `idx_bilinc_entries_fts` also indexes `metadata::text` (`storage/postgres.py:337-345`), so its pages keep tokens of the legacy text until vacuum or reindex. This is the same gap as backlog item PG-VACUUM, and the script says so rather than claiming physical removal. The app-maintained `tsv` column is not affected: it reads only the allowlisted fields in `FTS_METADATA_FIELDS` (`postgres.py:44, 73-86`).
- It does not touch `memory_events` payloads, `audit_log` values or snapshot files. Events and audit rows commit to their payload with a stored hash, so rewriting them would break the chain checks, and a purge of the key already removes them. Old snapshot files are backlog item A7. After this change those places keep legacy text until the key is purged; no new copy is made.
- Running it on the owner's `~/bilinc.db` or on production is an owner step (backlog LOCAL-REPAIR and PREV-VAL-PROD). The worker ships the script and tests only and touches no real database.

## Test plan (tests first, small commits)
Postgres tests run under the DSN gate; SQLite tests always.
1. The helper and `MemoryEntry(metadata={"previous_value": "x", "keep": 1})` has no `previous_value` and still has `keep`; the caller's dict is not mutated; `from_dict` and a snapshot round trip behave the same.
1b. `commit_with_agm_async` of a NEW key with `metadata={"previous_value": "secret text"}`: the stored row, the event payload and the audit `after_value` have no `previous_value`, on both backends.
2. Seed a legacy row (raw SQL: metadata with `previous_value`) on both backends. After each of `confirm`, `revise` with the same value, a `consolidate` of that key, a TTL rewrite and a rollback restore from a snapshot that holds the legacy entry: the stored row, the newest audit `after_value`, the newest event payload and the new snapshot file hold no `previous_value` and none of the seeded text. Revision of a different value still stores `previous_value_sha256` (existing tests at `tests/test_mcp_server_v2.py:461-462`, `tests/test_forget_state_sync.py:104-105` stay green).
2b. Rollback and diff: take a snapshot (hosted) or an audit state (local) that holds a legacy entry, run the new code, then: hosted `rollback_preview` does not list keys whose content is otherwise unchanged as `update`, and `rollback_execute` leaves them unwritten (no new event or audit row); hosted `diff` with `to_snapshot_id=None` does not list them as `modified`; the local `StatePlane.rollback(ts)` writes nothing and adds no audit row for them. Each on SQLite and on Postgres (DSN-gated).
2d. Version token: take `entry_version` of a seeded legacy row as computed from its raw stored state. Under the new code, `confirm` and `revise` with that token answer the normal `version_conflict` and do not crash; a fresh read then returns a token that is stable across reads and that a following `confirm` accepts. SQLite and Postgres (DSN-gated).
2b2. Hosted `diff` between an old legacy snapshot and a clean newer snapshot of the same content lists no `modified` key.
2c. Local `diff`: for a key with an old audit row that holds legacy `previous_value` text, the returned `before`/`after` entries contain no seeded text, and the audit rows themselves are unchanged (chain still verifies); a key whose only change between the two timestamps is the removal of `previous_value` is not listed as `modified`. SQLite and Postgres audit.
3. Scrub script, SQLite: default run counts the legacy rows and the file is byte-identical afterwards (hash before and after); `--execute` without `--backup-dir` exits non-zero and changes nothing; with it, the backup exists and opens with the same row count, only `previous_value` is removed (other metadata keys survive), a row with malformed JSON metadata is left alone and reported, a second run finds nothing; after `--execute` the seeded text is not in the raw bytes of the database file or of its `-wal` file, and the backup has mode 0600. With a second connection holding a write lock, `--execute` changes nothing and exits non-zero.
4. Scrub script, Postgres: default run changes no row (`schema_version` and counts unchanged, no `init()`); `--execute` removes the key and keeps other metadata keys; a schema without the table is skipped and reported; twice is safe.
5. Run through `bilinc-test` only: `-q -m public_source`, `-q -m internal_runtime`, the Postgres tests, and `.venv/bin/ruff check`.

## Rollback and who runs what
- Code: revert the commit. No schema change.
- The scrub removes a metadata key for good. Way back: the count-only run first; the SQLite backup the script takes; the nightly off-site backup for production (not verified from here, the owner confirms before `--execute`). The old text is of a replaced value and is no part of the current memory, so what is lost is only the leftover copy.
- **Running the script on the owner's local database or in production is an owner step.** The worker ships code and tests only and touches neither.

## Release-chain impact
- **Where the code ships.** The changed modules (`core`, `cloud`, `storage`, `mcp_server`) and `scripts/` are pruned from the PyPI wheel and sdist (`MANIFEST.in`, `pyproject.toml` `packages`; `docs/repository-contract.md:13`). They ship in the hosted runtime and the internal source, not in the public package, so the scrub script runs from a repository checkout, not from `pip install`.
- **Version.** Whether this goes out as a runtime-only deployment or inside a synchronized version is the owner's decision. If a version number moves, the whole chain moves with it: `pyproject.toml`, `bilinc.__version__`, `server.json` and the MCP registry entry, the hosted runtime image and any site version display (`tests/test_public_truth_contract.py` requires one version).
- **SDK behaviour, site code, MCP tool list:** unchanged. No API, tool schema or response field changes.
- **One-time version token change.** The hosted `entry_version` is a sha256 of `entry.to_dict()` (`cloud/runtime.py:122-130`; read at `653-658`, checked at `1256-1257`). Stripping `previous_value` at load changes the token of every legacy row once, and the scrub script changes it again for a row it cleans. A client that read a token before the deploy and sends it back as `expected_version` on `confirm` or `revise` gets one `version_conflict` although nothing visible changed; a fresh read fixes it. This goes into the ready note and the release note.
- **Migration:** none; the scrub is an owner-run command.
- **Public text:** nothing may claim old values are gone from history: events, audit rows and older snapshot files keep legacy text until the key is purged. Wording rule stays "removed from storage and history" for a purge only.
