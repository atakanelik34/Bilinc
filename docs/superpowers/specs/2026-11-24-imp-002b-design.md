# IMP-002b: the local MCP `revise` judges a reloaded memory against its stored importance

Date: 2026-11-24. Branch `vm/imp-002b` from origin/main `29ed56d` (2.7.3). Found by the IMP-002 design
gate (state/gate-imp-002-design-1.txt, note 3); verified here against the code.

## Problem

The local stdio server restores AGM beliefs at startup only for rows with importance >= 0.5
(mcp_server/hermes_stdio.py:43-49 -> adaptive/agm_engine.py:137-152, skip at 144). The MCP `revise`
handler (`_handle_revise`, mcp_server/server_v2.py:1386-1500) loads the stored row and calls
`plane._refresh_cached_belief(key, previous_entry)` (server_v2.py:1421-1424), but that helper leaves
keys without a cached belief alone by design (core/stateplane.py:3594-3609: "startup deliberately
loads only some rows as beliefs"). Then `plane.agm_engine.revise(entry, strategy=...)` finds no
existing belief and takes the "expand_new_key" branch (agm_engine.py:411-420), which accepts the
write whatever its importance.

Effect: in one process, a key committed at importance 0.3 has entrenchment 0.3, and an MCP `revise`
at 0.2 under the default ENTRENCHMENT strategy is refused. After a restart (or from a second local
process that never loaded the key) the same `revise` at 0.2 is accepted. This is the opposite of
IMP-002 (where the commit path refused too much); same root: a stored row the cache does not hold is
judged without its stored importance.

Reference behaviour: the hosted revise (`_revise_loaded`, cloud/runtime.py:1245-1250) puts the stored
row into the belief cache when the cached belief is missing or stale and sets its entrenchment from
the stored importance before revising. `_sync_cached_state` (core/stateplane.py:3563-3564) does the same.

## Approaches

1. **In `_handle_revise`, after `_refresh_cached_belief`, when a stored row exists and no belief is
   cached, add the stored row as the belief and set its entrenchment from its importance.** Local
   revise then decides against what is stored, like the hosted revise. Only the revise path changes.
2. **Make `_refresh_cached_belief` load uncached keys too.** It is also called on recall
   (server_v2.py:1235) and at server_v2.py:1606; every read would start filling the belief cache,
   which its docstring rules out on purpose (memory, belief counts). Rejected.
3. **Load every row as a belief at local startup (drop the 0.5 gate).** Changes startup cost and
   belief counts, and still misses a key written by another process after startup. Rejected (same
   reason as IMP-002's approach 2).

## Choice: approach 1

Smallest change at the place that decides, and it makes local `revise` follow the hosted rule.
The add uses `_sync_cached_state(key, previous_entry)` rather than two raw calls, so the belief, the
entrenchment and the graph stay in step exactly as on the other reload paths (it adds the belief,
sets entrenchment from importance, and refreshes the graph node; stateplane.py:3551-3570). A cached
belief that `_refresh_cached_belief` already synced is left as it is (its entrenchment was set there).

Out of scope: a cached belief that is current but whose row another process *updated* without
changing value or `updated_at` (not possible: an update moves `updated_at`); the commit path (IMP-002,
separate branch); hosted (already correct).

## Test plan (test first; `bilinc-test` only; local stdio is SQLite only)

New `tests/test_local_revise_after_restart.py`. A "restart" is a second `StatePlane` on the same SQLite
file, set up like `hermes_stdio` (init, `init_agm`, `load_beliefs_from_entries(list_all())`). Every
write uses a different value (the same value is a no-op success that skips the check).
1. Stored at 0.3 by plane A (`commit_with_agm_async`); restarted plane B: `_handle_revise` at 0.2 under
   the default strategy is refused and the stored row is unchanged. Red on 29ed56d.
2. Same before and after a restart: for (stored, new) in {(0.3, 0.2), (0.3, 0.3), (0.3, 0.6),
   (0.7, 0.6), (0.7, 0.8)}, `_handle_revise` on the same plane right after the commit and on a
   restarted plane give the same success value, equal to `new >= stored`.
3. Strategy still honoured: after a restart, `_handle_revise` at 0.2 with `strategy: "recency"` is
   accepted (guards against "always refuse").
4. A key with no stored row is still a new key: `_handle_revise` on an unknown key at 0.1 is accepted.
5. Graph and audit unchanged in shape: after an accepted revise on a restarted plane, the audit row's
   `before_value` is the stored row and the knowledge graph holds the new value (the
   `_sync_cached_state` path does not leave a stale node).
6. Regression pin (green on 29ed56d too): on one plane commit at 0.9, `_handle_revise` to 0.6 with
   `strategy: "recency"`, then `_handle_revise` at 0.7 under the default strategy is refused (the
   in-process entrenchment 0.9 is kept; no reads between the writes).

Mutation checks: drop the added call (1, 2 fail); call it unconditionally, also when a belief is
cached (6 fails); add the belief without setting its entrenchment (1 fails).
Also run tests/test_local_tools_freshness.py, tests/test_local_correctness.py, tests/test_agm_engine.py,
tests/smoke, and the full gate: `bilinc-test -q -m public_source`, `-m internal_runtime`, `ruff check`.
