# B4b: create-only commit (`if_absent`) in the Cloud MCP adapter and the CLI

Date: 2026-11-24. Branch `vm/b4b` from origin/main `29ed56d` (2.7.3). Backlog rank 15b (parity).

## Problem

A create-only commit ("write only if the key does not exist yet") is reachable from the SDK but not
from the two other public surfaces built on it:
- SDK: `CloudClient.commit(..., if_absent=...)` puts `ifAbsent` on `POST /api/cloud/memory/commit`
  (client.py:997-1019), since 0c3520b (2026-11-09), shipped in 2.7.0 together with the dream pass that
  uses it; covered by tests/test_dream_sdk.py:65-80.
- Hosted sidecar: `ProjectRuntimeManager.commit(..., if_absent=True)` is create-only inside the
  per-project mutation lock and raises `memory_exists` for an existing key (cloud/runtime.py:794-812);
  the service maps it to 409 (cloud/service.py `_ERROR_STATUS`), advertises the `commit_if_absent`
  capability on `/health` (service.py:37, 242), and the SDK knows `memory_exists` as canonical 409
  (client.py:55).
- Missing: the Cloud MCP tool `commit_mem` (cloud_mcp.py:77-111) has no `if_absent` parameter, and the
  CLI `bilinc commit` (cli/main.py:480-489, 762-773) has no flag. An agent using the MCP adapter cannot
  do a create-only write at all; it can only `commit` (create or revise).

The wire name is no longer open: the field is the one the SDK already sends. What this repo cannot
show is whether the live public route honours it: the sidecar does (runtime.py:794-815), and
service.py:241-243 describes a guard between the control plane and the sidecar, but nothing here shows
that `POST /api/cloud/memory/commit` takes a caller's `ifAbsent` and forwards it. This is the open
owner question G8 / open question 3 of the improve plan 006 (state/improve-2026-11-10/006, lines 88,
188-190). The SDK cannot detect an ignored flag: nothing in the reply shows it (G8). If the route
ignored the field, a create-only write would silently overwrite another writer's memory. The SDK
already made this promise in 2.7.0 (CHANGELOG.md:65); that is a related risk for the owner, not
evidence that the route works.

**Deployment precondition (owner, before release):** see Release-chain impact. This change only exposes
the existing SDK option on two more surfaces; it ships only if the live check passes.

## Approaches

1. **Pass-through parameter on both surfaces.** `commit_mem(..., if_absent: bool | None = None)` and
   `bilinc commit --if-absent`, both handed to `CloudClient.commit(if_absent=...)`. With the default the
   payload is byte-for-byte what it is today (`None` is omitted by `_put_optional`). An existing key
   surfaces as the SDK's `BilincConflictError` with code `memory_exists`, like every other conflict.
2. **A separate MCP tool (`create_mem`) and CLI command.** Clearer name, but it changes the tool list
   (docs/public/product-truth.json `cloud_mcp.tools`, the 13-tool connector count, client guides) for a
   flag the SDK models as an option of commit. Rejected.
3. **CLI only.** Leaves the MCP adapter, the surface agents use, without create-only. Rejected.

## Choice: approach 1

Same shape as the SDK, no new tool, no change to anyone who does not pass the option.

Decisions:
- MCP default is `None`, not `False`: the tool must not start sending `"ifAbsent": false` on every
  commit (the payload stays unchanged for existing callers and for a control plane that does not read
  the field).
- CLI flag is `--if-absent` (`store_true`); without it the CLI passes `None`.
- No client-side capability probe (unlike list `order`/`sources`): the reply carries nothing to check,
  so a probe is not possible from the client (G8). Protection is the owner's live check before release
  (below), not code here.
- Docstring of `commit_mem`: the first paragraph starts "By default," (so create-or-revise covers calls
  without `if_absent`), then one sentence: with `if_absent=true` the write only creates; an
  existing key is left untouched and the call fails with `memory_exists` (use `revise` to change it).
  CLI `--help` text says the same in one line.

Out of scope: the remote connector at mcp.bilinc.space and the site (not in this repo; whether its
`commit_mem` should also take `if_absent` is the owner's call with the site work); the local stdio
server (local `commit` has no create-only mode; a separate question).

## Changes

- `src/bilinc/cloud_mcp.py` `commit_mem`: parameter `if_absent: bool | None = None`, passed through;
  docstring sentence.
- `src/bilinc/cli/main.py`: `commit.add_argument("--if-absent", action="store_true", help=...)`; the
  commit branch passes `if_absent=True if args.if_absent else None`.
- `CHANGELOG.md`: new `## [Unreleased]` / `### Added` above `## [2.7.3]`, one bullet.
- README: README.md:96 is inside a bash code block, so the line goes as one plain sentence right after
  that code block, exactly:
  `Add --if-absent to write only when the key does not exist yet; if it does, the command fails with memory_exists.`
  No wording about coordination, claiming tasks or multi-agent use.

## Test plan (test first; `bilinc-test` only)

New `tests/test_create_only_surfaces.py` (internal_runtime lane like the other SDK/MCP tests; the
network is faked with a recording transport / `client._open`, no real key; CLI env isolated like
tests/test_cli_error_paths.py):
1. MCP: `build_server().call_tool("commit_mem", {"key": "k", "value": 1, "if_absent": True})` sends
   `ifAbsent: true`; without the argument the payload has no `ifAbsent` key (same payload as on
   29ed56d). Red on 29ed56d (unknown argument).
2. MCP schema: `list_tools()` shows `if_absent` on `commit_mem`, optional (not in `required`), boolean
   or null; the tool list (names) is unchanged.
3. MCP: a 409 `memory_exists` answer surfaces as an error, not a success: the test accepts either a
   raised `ToolError` whose message contains `memory_exists`, or an `isError` result whose text contains
   it (depends on the mcp version); a silent success fails the test, and the submitted value must not
   appear in the error text.
4. CLI: `main(["commit", "--key", "k", "--value", "v", "--if-absent"])` sends `ifAbsent: true`; without
   the flag no `ifAbsent` key. Red on 29ed56d (unknown flag).
5. CLI: a 409 `memory_exists` answer prints `bilinc: error:` with the code and returns 1.
6. Pins: SDK `commit(if_absent=...)` payloads unchanged (tests/test_dream_sdk.py:68-80 keep passing);
   docs/public/product-truth.json tool names unchanged (tests/test_public_truth_contract.py keeps
   passing).
Mutation checks: MCP default `False` instead of `None` (1 fails: `ifAbsent: false` appears); drop the
pass-through in MCP (1 fails); CLI passes `False` without the flag (4 fails).
Full gate: `bilinc-test -q -m public_source`, `-m internal_runtime` (Postgres runs; no backend path
changes), `ruff check`.

## Release-chain impact

- **Owner check before release (G8):** against the live route, on a throwaway key in a test
  project: `commit(key, "first", if_absent=True)`, then `commit(key, "second", if_absent=True)`. The
  second must fail with 409 `memory_exists` and a recall/history of the key must still show `"first"`.
  If it does not, hold this change back (or at least the `commit_mem` docstring and the CLI help text)
  and raise the 2.7.0 SDK promise as a separate fix; do not ship the promise.
- PyPI package: yes (cloud_mcp.py, cli/ are in the wheel). Ships only in a release the owner runs.
  Additive: one optional MCP tool parameter, one CLI flag; no new tool, export or error code.
- MCP registry: the `server.json` version moves with the PyPI version in the same owner-run release
  (no schema text to edit); the tool list is unchanged; the `commit_mem` input schema gains an optional field
  (a client that caches schemas sees it after the release).
- Remote connector / site: no change here; owner decides whether the connector's `commit_mem` gets
  the same option.
- Hosted runtime, migration: none. Rollback: revert.
- CHANGELOG `[Unreleased]` heading conflicts trivially with the other ready branches.
