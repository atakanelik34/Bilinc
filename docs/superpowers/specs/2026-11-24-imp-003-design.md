# IMP-003: timeouts reach SDK callers as Bilinc errors; `python -m bilinc.cli` returns its exit code

Date: 2026-11-24. Branch `vm/imp-003` from origin/main `29ed56d` (2.7.3). Source: improve plan
`state/improve-2026-11-10/003-sdk-network-errors-and-cli-exit-code.md` (written at 085bb99). The SDK
transport changed in 2.7.2 (own opener `_open`, redirect handling); everything below was re-read on
29ed56d. This is the public package (`pip install bilinc`): it ships only in a release the owner runs.

## Problem

1. `_default_transport` (src/bilinc/client.py:857-924) maps two kinds of failure:
   `urllib.error.HTTPError` (status errors, refused redirects) and `urllib.error.URLError` (errors while
   sending: DNS, refused connection, TLS handshake) to `BilincCloudError` subclasses. urllib does not
   wrap failures that happen after the request was sent: a timeout while waiting for the status line or
   while `response.read()` runs, or a dropped connection, arrive raw (`TimeoutError`,
   `ConnectionResetError`, `http.client.RemoteDisconnected`, `http.client.IncompleteRead`, an
   `ssl.SSLError` mid-read). Consequences on 29ed56d:
   - `except BilincError` in user code does not catch them;
   - reads are not retried: `_with_read_retries` (client.py:1657-1672) only retries `BilincCloudError`
     with `retryable=True`;
   - every CLI command except `bilinc wiki` prints a traceback: the dispatcher catches only
     `(BilincApiKeyRequired, BilincCloudError, ValueError)` (cli/main.py:937);
   - `dream_apply` loses its partial results: it attaches `exc.partial` only on `BilincCloudError`
     (client.py:1229-1234).
   The repo already works around it once: `bilinc wiki` has its own `RAW_NETWORK_ERRORS =
   (OSError, http.client.HTTPException)` (wiki/fetch.py:46) and cli/main.py:339.
2. `python -m bilinc.cli` ignores the return value of `main()` (cli/__main__.py: `main()`), so it exits
   0 even when the command failed; `python -m bilinc.cli.main` and the `bilinc` console script exit
   with the code (cli/main.py:944 `raise SystemExit(main())`).

## Approaches

1. **Wrap the remaining network errors once, at the single network boundary.** Add a third clause after
   the two existing ones in `_default_transport`: `except (OSError, http.client.HTTPException)` raises
   `BilincConnectionError(code="connection_failed", retryable=True)` with the original as `__cause__`.
   Order matters: `HTTPError` is a `URLError` is an `OSError`, so the new clause must be last. Every
   consumer (read retries, CLI, `dream_apply`, `login`) then works without edits.
2. **Catch the raw errors at each consumer**, as `bilinc wiki` did. That is how the gap spread; every new
   consumer would have to remember it. Rejected.
3. **A new error class (`BilincTimeoutError`) or a new code.** More public surface (`__all__`,
   `CANONICAL_ERROR_CODES`, product-truth, site docs) for no behaviour a caller cannot get from `code`
   and `__cause__`. Rejected.

## Choice: approach 1

The fix belongs where the network is touched. Retry semantics, decided:
- The error is `retryable=True` with code `connection_failed`, like the existing `URLError` mapping;
  `connection_failed` is already in `RETRYABLE_ERROR_CODES` (client.py:70).
- Reads are retried by the existing bounded loop. Reads are POSTs too (client.py:1639), so retryability
  cannot be keyed on the HTTP method.
- Writes are never retried automatically (client.py:231-233, 1660-1661); this change only changes which
  exception a failed write raises. Because the failure can happen after the service received the write,
  the message says so ("the request may have reached Bilinc Cloud"), and the docstring of
  `BilincConnectionError` gets one sentence: after a write, `connection_failed` does not prove the write
  was not applied; pass `idempotency_key` to retry safely.

Two details found by the design gate (round 1):
- `_default_ssl_context()` runs inside the `try` today (client.py:866-870). A missing or unreadable
  `BILINC_CA_BUNDLE` / `SSL_CERT_FILE` raises `FileNotFoundError`, a malformed bundle `ssl.SSLError`;
  both are `OSError`s, so the new clause would label a local configuration error as "may have reached
  Bilinc Cloud" and reads would retry it with back-off. The context is therefore built before the `try`;
  such errors stay what they are today (raised unchanged, not retried).
- The `HTTPError` clause reads the error body (`detail = exc.read()`, client.py:902) inside its own
  handler, where the new sibling clause cannot catch a timeout or reset. That read is wrapped: on
  `(OSError, http.client.HTTPException)` the body counts as empty and the status mapping still applies
  (a slow 503 stays `BilincRuntimeUnavailableError`, not a raw `TimeoutError`).

Out of scope (unchanged): `RAW_NETWORK_ERRORS` in wiki/fetch.py and cli/main.py:339 (a caller-supplied
`transport` can still raise raw errors, and the wiki writer raises real file-system `OSError`s through the
same path); redirect handling and the 2.7.2 security checks (their errors are `BilincConnectionError`
already, raised inside the `HTTPError` clause, and are not `OSError`s); `login.py` (already catches
`BilincCloudError`); the SDK version number and docs/public/product-truth.json.

## Changes

- `src/bilinc/client.py`: `import http.client`; in `_default_transport` build
  `context = _default_ssl_context()` before the `try` and pass it in; wrap the error-body read in the
  `HTTPError` clause (fallback `detail = ""`); third `except (OSError, http.client.HTTPException)`
  clause after the `URLError` clause; message
  `"Bilinc Cloud request failed after it was sent (the request may have reached Bilinc Cloud): <reason>"`
  where `<reason>` is `str(exc) or type(exc).__name__`; one docstring sentence on
  `BilincConnectionError`. Existing clauses and messages unchanged.
- `src/bilinc/cli/__main__.py`: `raise SystemExit(main())`.
- `CHANGELOG.md`: two plain bullets in a new `## [Unreleased]` / `### Fixed` section above `## [2.7.3]`
  (line 5); the old `## [Unreleased] — 2026-05-17` block at line 443 stays as it is.
- `dream_apply` docstring: after a `connection_failed`, `exc.partial["pages_done"]` is a lower bound
  (the service may have applied the page that timed out).

## Release-chain impact

- Release-note items: reads that time out while waiting for the answer are now retried (bounded, 3
  attempts; with the default 30 s timeout a failing `bilinc status` can take about 90 s plus back-off
  before it reports); this change has no SQLite/Postgres-specific path, the Postgres suite runs in the
  full gate as regression only.

- PyPI package: **yes** (client.py and cli/ are in the wheel, pyproject.toml:78). Ships only in a release
  the owner runs (version number, PyPI, MCP registry, GitHub release, public mirror). No API addition: the
  exported names and error codes are unchanged. Behaviour change for the release notes: code that
  caught the raw `TimeoutError` / `OSError` from the SDK will no longer see it (`BilincConnectionError`
  is not an `OSError`); it must catch `BilincError` / `BilincConnectionError` instead. The raw error
  stays reachable as `__cause__`.
- Docs: grep of README.md and docs/ (excluding docs/superpowers) on 29ed56d finds no text on which
  exceptions the SDK raises or what `connection_failed` means; docs/public/product-truth.{md,json} only
  list the exported names, which do not change. The site docs are not in this repo: the owner checks
  them at release.
- Hosted runtime, site: no change. cloud_mcp (in the wheel) benefits through the SDK, no code change.
- Migration: none. Rollback: revert.
