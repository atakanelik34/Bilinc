# IMP-002: a memory saved with low importance stays writable after a restart

Date: 2026-11-24. Branch `vm/imp-002` from origin/main `29ed56d` (2.7.3). Source: improve plan
`state/improve-2026-11-10/002-low-importance-commit-after-restart.md` (written at 085bb99); every line
below was re-read on 29ed56d.

## Problem

A key committed with importance below 0.5 can be committed again while the process runs, but the
same commit is refused after a restart (or after the project's plane is unloaded and reloaded): the
hosted route answers 409 `commit_rejected`, and the refusal repeats for every importance below 0.5.
The improve audit reproduced it on 085bb99 with the hosted runtime on SQLite (v1 0.3 saved, v2 0.3
saved, restart, v3 0.3 refused, v4 0.4 refused).

Cause, all unchanged on 29ed56d:
- Startup loads beliefs only for rows with importance >= 0.5 and sets their entrenchment
  (adaptive/agm_engine.py:137-152, skip at 144).
- A key with no recorded entrenchment counts as 0.5 (agm_engine.py:161-163), and the default
  ENTRENCHMENT strategy accepts a revision only when `new.importance >= old entrenchment`
  (agm_engine.py:200-203).
- `StatePlane.commit_with_agm_async` reconciles the belief cache with the stored row before revising
  (core/stateplane.py:3772-3787): when the cached belief is missing or older than the row it calls
  `add_belief(previous_entry)` but does not set the entrenchment. After a restart the low-importance
  key gets its belief back with no entrenchment, is compared with the default 0.5, the revision is
  rejected, nothing is saved, and the entrenchment never changes, so every retry fails too.

The two other places that put a stored row into the belief cache already set the entrenchment from
the row: `_sync_cached_state` (core/stateplane.py:3563-3564) and the hosted `_revise_loaded`
(cloud/runtime.py:1248-1250, `if _belief_is_stale(...): set_entrenchment(key, importance)`).

`commit_with_agm_async` is the write path of the hosted `commit` (cloud/runtime.py:816) and of the
local MCP server (mcp_server/server_v2.py:1147-1148, 2334), so both modes have the bug and both get
the fix.

## Approaches

1. **Set the entrenchment from the stored row where the commit path reconciles the belief cache.**
   In the same `if` that calls `add_belief(previous_entry)`, also call
   `set_entrenchment(key, float(previous_entry.importance))`. One line; mirrors `_sync_cached_state`
   and `_revise_loaded`; the decision then depends on the stored row, not on whether this process
   happened to load the key at startup or write it itself.
2. **Drop the `importance < 0.5` gate in `load_beliefs_from_entries`.** Fixes the restart case only,
   not a row first written by another process; loads every row as a belief at startup, which changes
   belief counts, stats and memory per plane. Rejected.
3. **Change the default entrenchment from 0.5 to 0.0.** Changes the AGM outcome for every key without
   a recorded entrenchment, beyond this bug, and is pinned by tests/test_agm_engine.py. Rejected.

## Choice: approach 1

It fixes the cause where it is, for both modes, with the rule two sibling code paths already use.

What it does not change (out of scope, said in the release note):
- The staleness test on the same lines (`previous_entry.created_at > cached.created_at`) misses a row
  another process *updated* (upsert keeps `created_at`). That is a separate gap; the fix only adds
  the entrenchment inside the existing branch.
- When the cached belief is present and current, its entrenchment is left alone, so AGM's
  "keep the higher entrenchment of a replaced belief" inside one process is unchanged.
- `load_beliefs_from_entries`, the 0.5 default and `cloud/runtime.py` are not touched.
- The local MCP `revise` (mcp_server/server_v2.py:1421-1461) does not load an uncached key through
  `_refresh_cached_belief`, so after a restart a low-importance key is accepted as `expand_new_key` at
  any importance, where in-process it would be refused: the opposite inconsistency. Found by the
  design gate; added to the backlog as IMP-002b, not fixed here.

## Changes

- `src/bilinc/core/stateplane.py` `commit_with_agm_async`: inside
  `if cached is None or previous_entry.created_at > cached.created_at:` add
  `self.agm_engine.set_entrenchment(key, float(previous_entry.importance))` after `add_belief`, with a
  one-line comment (a key loaded from storage is judged against its stored importance, as in
  `_sync_cached_state` and the hosted revise).
- `CHANGELOG.md` `[Unreleased]` / `### Fixed`: one plain bullet.

## Test plan (test first; `bilinc-test` only)

Every commit in these tests writes a different value: the same value is a no-op success inside
`revise` (adaptive/agm_engine.py:438-455) and would never reach the entrenchment check. Tests 1 and 3
are shown red on 29ed56d.


New `tests/test_commit_after_restart.py`:
1. Hosted, SQLite and Postgres (throwaway schema on `BILINC_TEST_POSTGRES_DSN`): commit `low.key` at
   0.3, commit again at 0.3 (saved), close the manager, build a new `ProjectRuntimeManager` on the
   same folder, commit at 0.3 and at 0.4: both saved, the stored value is the last one. Red on 29ed56d.
2. Same before and after a restart, hosted, both backends: for stored importance s and new importance
   n in {(0.3, 0.2), (0.3, 0.3), (0.3, 0.6), (0.7, 0.6), (0.7, 0.8)}, the accept/reject outcome of the
   second commit is the same when it runs in the same process as the first commit and when it runs
   after a restart. (Rows with s >= 0.5 already worked; they pin that nothing changes for them.)
3. Local: two `StatePlane`s on one SQLite file (stand-in for two stdio processes or a restart); plane
   A commits `low.key` at 0.3; plane B (fresh, never saw the key) commits it at 0.3: saved.
4. Rejection still works after a restart: stored 0.3, new 0.2 is refused and the stored row is
   unchanged (guards against "always accept").
5. In-process entrenchment kept: in one process commit at 0.9, then revise the key to importance 0.6
   under a strategy that accepts it regardless of entrenchment (e.g. recency), so the stored row says
   0.6 while the cached belief is current and AGM keeps entrenchment 0.9; a default commit at 0.7 is
   refused, as on 29ed56d. This is a regression pin, not a red-first test: it is shown green on
   29ed56d during the build, and no recall or load runs between the commits (reads call
   `_refresh_cached_belief`, core/stateplane.py:3594-3609, which resets entrenchment on an
   `updated_at` change). Hosted, both backends.

Mutation checks before the code gate: remove the added line (1, 3 fail); set the entrenchment to 0.0
instead of the stored importance (4 fails); set it unconditionally outside the `if` (test 5 fails).

Also run the existing AGM suites (tests/test_agm_engine.py, tests/test_agm_operation_log.py,
tests/test_local_correctness.py, tests/smoke) and the full gate: `bilinc-test -q -m public_source`,
`-m internal_runtime` (Postgres runs), `ruff check`.
