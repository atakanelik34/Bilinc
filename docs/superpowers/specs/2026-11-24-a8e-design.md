# A8e: a snapshot's root hash is read from the store, not this process's cache

Date: 2026-11-24. Branch `vm/a8e` from origin/main `29ed56d`. Follow-up of A8d (merged).

## Problem

`StatePlane.snapshot()` (src/bilinc/core/stateplane.py:3511-3544) reads every entry from the
backend (`_persistent_state`, stateplane.py:363-367, a fresh `list_all()`), but takes `root_hash`
from `self.audit.get_root_hash()` (stateplane.py:3530), which is the process-local cached head.
When another writer appended to the audit chain since this process last wrote (a second hosted
worker, or, locally, a second MCP stdio process on the same SQLite file), the snapshot holds the
other writer's entries under an older root.

Where that stale root goes:
- hosted `create_snapshot` stores it as the checkpoint's `root_hash` (cloud/runtime.py:1544-1551);
  it is shown later as `from_root_hash` / `to_root_hash` in diff (runtime.py:1623-1653) and as
  `target_root_hash` in rollback preview (runtime.py:1688-1709);
- the SNAPSHOT memory event's `checkpoint_root` (stateplane.py:3533-3538);
- local stdio `snapshot` tool and the `_handle_snapshot` backend snapshot (server_v2.py:735, 1669).

Other display-only cache reads of the same value: `verify` result `root_hash` (stateplane.py:3503),
`stats()` (stateplane.py:3666), health readiness (observability/health.py:128).

No binding check uses the snapshot's root today: A8d made the rollback execute check and the
preview's `current_root_hash` read the store (`fresh_state_version`, runtime.py:253-262). So this is
a correctness-of-record issue, low severity, not a data-loss path.

Facts the design rests on:
- Chain appends read the head inside the write transaction (SQLite `BEGIN IMMEDIATE` + `SELECT
  root_hash ... ORDER BY id DESC LIMIT 1`, core/audit.py:196-205; Postgres trail likewise per A8a).
  The cache is never used as `prev_root`, so refreshing it has no effect on chain integrity.
- `refresh_root_hash()` exists on `AuditTrail` (core/audit.py:340-351) and `SyncPostgresAuditTrail`
  (core/postgres_audit_sync.py:425-432); a failed read raises. The async `PostgresAuditTrail` has
  none and no caller builds a StatePlane with it (A8d note).
- Writes save to the backend first and log to the audit chain after (e.g. stateplane.py:525/562,
  3620/3634). So between a backend save and its audit row there is a window where the entry is
  visible but the chain head has not moved yet.

## Approaches

1. **Refresh once, before the state read.** Same order A8d used for the preview: a write landing in
   between makes the root older than the entries, never newer. One extra indexed query. Leaves the
   "fresh entries under an older root" case open whenever a write lands during `list_all()`, which
   is exactly the case this item is about, only narrower.
2. **Refresh before and after the state read; accept only a stable head, retry a bounded number of
   times.** Read head H1, read entries, read head H2. If H1 == H2, no audited write committed its
   chain row during the read; record H1. Otherwise retry (3 attempts total); if the head never holds
   still, raise `snapshot_state_unstable` (hosted callers surface a retryable error; nothing is
   written to disk or to the event log). Two extra indexed queries per snapshot, more only under
   concurrent writes. Catches every write whose audit row commits during the read.
3. **Hold the cross-process write lock for the whole snapshot** (SQLite `BEGIN IMMEDIATE`, Postgres
   the chain lock). Fully consistent, but blocks every writer of the project for the length of a
   full `list_all()` plus `verify_integrity()`, adds new lock semantics to a read path, and differs
   per backend. Disproportionate for a record-keeping bug under a design that runs one writer.

## Choice: approach 2

It is the only option that turns "stale root" into either a correct root or an explicit error,
without new locks. Under the supported one-writer setup H1 == H2 on the first try, so behaviour and
output do not change there. Approach 1 is strictly weaker for the same code size; approach 3 costs
writer latency for a low-severity issue.

Residual limit, documented in the code and release note, not fixed: because writes save state
before logging, a write whose backend save lands during the read but whose audit row lands after H2
is in the entries without being in H2. Closing that needs approach 3 or audit-before-state ordering
(the latter is improve plan 001's territory; this item does not change write ordering).

## Changes

- `StatePlane._fresh_root_hash()` (new, private): `self.audit.refresh_root_hash()` when audit is on
  and the trail has the method; otherwise `self.audit.get_root_hash()` (only the unused async trail,
  noted in a comment); `None` when audit is off. A failed read raises; no fallback to the cache.
- `StatePlane.snapshot()`: the H1 / entries+stats / H2 loop above, 3 attempts, then
  `RuntimeError("snapshot_state_unstable")`. `root_hash` and the event's `checkpoint_root` take the
  stable head. `verify_integrity()` stays after the loop as today.
- Display reads switch to the fresh read: `verify` result (stateplane.py:3503), `stats()`
  (stateplane.py:3666), health readiness (health.py:128, already inside the try that marks audit
  failed on an exception). `cloud/runtime.py` `state_version` stays a cache read (A8d's reasoning:
  responses right after this process's own write carry that write's root).
- Hosted `create_snapshot`: maps `snapshot_state_unstable` to the existing retryable error path
  (check how runtime errors reach the service layer during build; if there is no retryable class,
  the message is passed through unchanged and the release note says so).
- CHANGELOG `[Unreleased]` line.

## Test plan (test first; `bilinc-test` only)

New `tests/test_snapshot_root_fresh.py`, SQLite and Postgres (throwaway DSN) where the trail differs:
1. Two StatePlanes on one store; B commits; A (stale cache) snapshots: `root_hash` equals B's head
   and the event `checkpoint_root` matches. Red on origin/main.
2. Hosted: two runtime managers on one project; worker 2 commits; worker 1 `create_snapshot`; the
   stored checkpoint, diff `from_root_hash` and preview `target_root_hash` show the fresh head.
3. Head moves during the read (backend `list_all` wrapped to append an audit row on the first call
   only): snapshot retries and records the second, stable head; called on every attempt: raises
   `snapshot_state_unstable`, writes no checkpoint file and no SNAPSHOT event.
4. Refresh failure (trail's `refresh_root_hash` raises): snapshot, `stats()` and `verify` raise;
   health marks audit failed; no cache fallback.
5. Single writer: snapshot right after its own commit gives that commit's root on the first attempt
   (one `list_all` call), output keys unchanged.
6. Audit disabled: `root_hash` None, no refresh call.
7. Display: `stats()` and `verify` show another writer's head.
Mutation checks before the code gate: cache read instead of refresh at each site; drop the H2
check; unbounded retry; fallback to cache on failure. Each must fail a test.
Full gate: `bilinc-test -q -m public_source`, `-m internal_runtime` (Postgres runs), `ruff check`.
