# A8e: a snapshot's root hash is read from the store, not this process's cache

Date: 2026-11-24. Branch `vm/a8e` from origin/main `29ed56d`. Follow-up of A8d (merged).

## Problem

`StatePlane.snapshot()` (src/bilinc/core/stateplane.py:3511-3544) reads every entry from the
backend (`_persistent_state`, stateplane.py:363-367, a fresh `list_all()`), but takes `root_hash`
from `self.audit.get_root_hash()` (stateplane.py:3530), which is the process-local cached head.
When another writer appended to the audit chain since this process last wrote (a second hosted
worker, or, locally, a second MCP stdio process on the same SQLite file), the snapshot holds the
other writer's entries under an older root.

Where that stale root goes:
- hosted `create_snapshot` stores it as the checkpoint's `root_hash` (cloud/runtime.py:1544-1551);
  it is shown later as `from_root_hash` / `to_root_hash` in diff (runtime.py:1623-1653) and as
  `target_root_hash` in rollback preview (runtime.py:1688-1709);
- the SNAPSHOT memory event's `checkpoint_root` (stateplane.py:3533-3538);
- local stdio `snapshot` tool and the `_handle_snapshot` backend snapshot (server_v2.py:735, 1669).

Other display-only cache reads of the same value: `verify` result `root_hash` (stateplane.py:3503),
`stats()` (stateplane.py:3666), health readiness (observability/health.py:128).

No binding check uses the snapshot's root today: A8d made the rollback execute check and the
preview's `current_root_hash` read the store (`fresh_state_version`, runtime.py:253-262). So this is
a correctness-of-record issue, low severity, not a data-loss path.

Facts the design rests on:
- Chain appends read the head inside the write transaction (SQLite `BEGIN IMMEDIATE` + `SELECT
  root_hash ... ORDER BY id DESC LIMIT 1`, core/audit.py:196-205; Postgres trail likewise per A8a).
  The cache is never used as `prev_root`, so refreshing it has no effect on chain integrity.
- `refresh_root_hash()` exists on `AuditTrail` (core/audit.py:340-351) and `SyncPostgresAuditTrail`
  (core/postgres_audit_sync.py:425-432); a failed read raises. The async `PostgresAuditTrail` has
  none and no caller builds a StatePlane with it (A8d note).
- Writes save to the backend first and log to the audit chain after (e.g. stateplane.py:525/562,
  3620/3634). So between a backend save and its audit row there is a window where the entry is
  visible but the chain head has not moved yet.

## Approaches

1. **Refresh once, before the state read.** Same order A8d used for the preview: a write landing in
   between makes the root older than the entries, never newer. One extra indexed query. Leaves the
   "fresh entries under an older root" case open whenever a write lands during `list_all()`, which
   is exactly the case this item is about, only narrower.
2. **Refresh before and after the state read; accept only a stable head, retry a bounded number of
   times.** Read head H1, read entries, read head H2. If H1 == H2, no audited write committed its
   chain row during the read; record H1. Otherwise retry (3 attempts total); if the head never holds
   still, raise `ValueError("version_conflict")` (an existing public code, see "Error surface";
   nothing is written to disk or to the event log). Two extra indexed queries per snapshot, more
   only under concurrent writes. Catches every write whose audit row commits during the read.
3. **Hold the cross-process write lock for the whole snapshot** (SQLite `BEGIN IMMEDIATE`, Postgres
   the chain lock). Fully consistent, but blocks every writer of the project for the length of a
   full `list_all()` plus `verify_integrity()`, adds new lock semantics to a read path, and differs
   per backend. Disproportionate for a record-keeping bug under a design that runs one writer.

## Choice: approach 2

It is the only option that turns "stale root" into either a correct root or an explicit error,
without new locks. Under the supported one-writer setup H1 == H2 on the first try, so behaviour and
output do not change there. Approach 3 costs writer latency for a low-severity issue.

Against approach 1 (round-1 gate asked to weigh this with the error surface priced in): because the
unstable case reuses an existing public code (below), approach 2 adds no SDK, PyPI, cloud_mcp or
site change; its extra size over approach 1 is the loop and one raise inside `snapshot()`, plus
tests. Approach 1 would leave exactly the case this item names (fresh entries under an older root
when a write lands during the read) open and documented; approach 2 closes it for every write whose
audit row commits during the read, at that small cost. If a new public code were needed, approach 1
plus the documented limit would be the better trade; it is not needed.

## Error surface (decided)

The unstable case raises `ValueError("version_conflict")`.
- Why this code: it already means "the state moved under a concurrent change; re-read and try
  again" (cloud_mcp.py:159, 387; commit/revise use it the same way). It is in the sidecar's
  `_PUBLIC_RUNTIME_ERRORS` and `_ERROR_STATUS` (409, cloud/service.py:150-180) and in the SDK's
  `CANONICAL_ERROR_CODES` (409, client.py:47-69), so `_runtime_errors()` (service.py:194-211) turns
  it into HTTP 409 `version_conflict` with no new mapping, and SDK callers get the known conflict
  error. It is not in `RETRYABLE_ERROR_CODES`, so the SDK does not auto-retry; the caller retries the
  snapshot like any other conflict. That is acceptable: the case needs a concurrent second writer,
  which the supported deployment does not run.
- Rejected: a new `snapshot_state_unstable` code. It would need `_PUBLIC_RUNTIME_ERRORS`,
  `_ERROR_STATUS`, the SDK lists (client.py ships in the wheel, so a PyPI release), cloud_mcp text
  and the control-plane/site mapping, for a case that does not occur in the supported setup.
- Local stdio: the `snapshot` tool (server_v2.py:733-737) is inside the tool dispatcher whose
  `except Exception` returns `_error_text(name, e)`, so the caller sees a `version_conflict` tool
  error. `_handle_snapshot` (server_v2.py:1667-1672) keeps its existing behaviour of reporting a
  backend snapshot failure as `backend_snapshot_error` next to the rest of its payload; unchanged and
  tested as such.

Residual limit, documented in the code and release note, not fixed: because writes save state
before logging, a write whose backend save lands during the read but whose audit row lands after H2
is in the entries without being in H2. Closing that needs approach 3 or audit-before-state ordering
(the latter is improve plan 001's territory; this item does not change write ordering).

## Changes

- `StatePlane._fresh_root_hash()` (new, private): `None` when audit is off, else
  `self.audit.refresh_root_hash()`. No cache branch: a trail without the method raises
  `AttributeError` (the only such trail, the async `PostgresAuditTrail`, is never given to a
  StatePlane). A failed read raises; no fallback to the cache.
- `StatePlane.snapshot()`: each attempt reads H1, then backend stats and entries, then
  `verify_integrity()`, then H2; the attempt counts only if H1 == H2, so `integrity` describes the
  same chain head that is recorded. 3 attempts, then `ValueError("version_conflict")`. `root_hash`
  and the event's `checkpoint_root` take the stable head; the SNAPSHOT event is appended only after a
  stable attempt.
- Display reads switch to the fresh read: `verify` result (stateplane.py:3503), `stats()`
  (stateplane.py:3666), health readiness (health.py:128, already inside the try that marks audit
  failed on an exception). Each of these already runs `verify_integrity()` over the full chain, so
  one more single-row read is negligible next to it. The "not on every read" sentence in both
  `refresh_root_hash` docstrings (core/audit.py:343-344, postgres_audit_sync.py:426) is rewritten to:
  use it where the head is recorded, compared or bound, or shown next to a full-chain check; plain
  responses after this process's own write keep the cache.
- Health thread safety: SQLite `refresh_root_hash` takes the trail's lock. `SyncPostgresAuditTrail`
  assigns `_root_hash` without a lock; that is safe because the assignment of a str is atomic, every
  value it can hold is a real head read from the store, and no code path uses the cache as a chain
  link (`log()` reads the head inside its transaction), so a race can only make a later cache read
  show an older real head, never corrupt the chain. `cloud/runtime.py` `state_version` stays a cache read (A8d's reasoning:
  responses right after this process's own write carry that write's root).
- Hosted `create_snapshot`: no change needed; the `version_conflict` from `plane.snapshot()` is raised
  before any file is written, and the endpoint already wraps the call in `_runtime_errors()` (checked
  in the build, with a service-layer test).
- CHANGELOG `[Unreleased]` line.

## Test plan (test first; `bilinc-test` only)

New `tests/test_snapshot_root_fresh.py`. Backend matrix: "both" means a parametrized test that runs
on SQLite (`AuditTrail`) and on Postgres (`PostgresBackend` + `SyncPostgresAuditTrail`, throwaway
schema on `BILINC_TEST_POSTGRES_DSN`; skipped only when the DSN is unset, and `bilinc-test` sets it).

| # | test | backends |
|---|---|---|
| 1 | Two StatePlanes on one store; B commits; A (stale cache) snapshots: `root_hash` equals B's head, the SNAPSHOT event's `checkpoint_root` matches. Red on origin/main | both |
| 2 | Hosted: two runtime managers on one project; worker 2 commits; worker 1 `create_snapshot`; the stored checkpoint, diff `from_root_hash` and preview `target_root_hash` show the fresh head | both (runtime with SQLite backend, and with Postgres backend) |
| 3 | Head moves during the read (backend `list_all` wrapped to append an audit row on the first call only): one retry, the second stable head is recorded and `integrity` matches it; wrapped on every call: raises `ValueError("version_conflict")`, writes no checkpoint file and no SNAPSHOT event | both |
| 4 | Refresh failure (`refresh_root_hash` raises): `snapshot()`, `stats()` and `verify` raise; health marks audit failed; nothing falls back to the cache | both |
| 5 | Single writer: snapshot right after its own commit gives that commit's root on the first attempt (one `list_all` call), output keys unchanged | both |
| 6 | Audit disabled: `root_hash` None, no refresh call | SQLite (no audit means no trail; backend-independent) |
| 7 | Display: `stats()` and `verify` show another writer's head | both |
| 8 | Service layer: `POST /v1/projects/{id}/snapshots` with the head moving on every attempt returns 409 with detail `version_conflict` (not 500) and leaves no checkpoint | SQLite runtime through the FastAPI app (error mapping is backend-independent; Postgres path covered by #3) |
| 9 | Local stdio: the `snapshot` tool returns a `version_conflict` tool error; `_handle_snapshot` reports it as `backend_snapshot_error` and still returns the rest of its payload | SQLite (stdio is local-only) |
Mutation checks before the code gate: cache read instead of refresh at each site; drop the H2
check; `integrity` taken outside the attempt; unbounded retry; fallback to cache on failure;
a new error code instead of `version_conflict`. Each must fail a test.
Full gate: `bilinc-test -q -m public_source`, `-m internal_runtime` (Postgres runs), `ruff check`.

## Release-chain impact

- PyPI package: none. The wheel ships only `bilinc`, `bilinc.cli`, `bilinc.wiki` (pyproject.toml:78)
  and MANIFEST.in prunes `core/`, `cloud/`, `mcp_server/`, `observability/` from the sdist.
- Hosted runtime: changes (snapshot, stats, health, verify); ships with the next synchronized
  version and redeploy. Local stdio runtime (owner's machine): same core change at its next update.
- SDK, site, MCP registry, cloud_mcp: no change (the unstable case reuses `version_conflict`, already
  canonical in the SDK and mapped by the sidecar). Migration: none. Rollback: revert the commit.
- Overhead: one to two extra indexed single-row reads per snapshot/stats/verify/health call; no
  measurement claimed.
