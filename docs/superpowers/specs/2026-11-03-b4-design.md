Backlog B4 lists four gaps. Checked against origin/main 5578d27:

| Gap | Status on main | Evidence |
|---|---|---|
| Cloud MCP `rollback` preview drops `limit` | open | `cloud_mcp.py:~279` calls `client.rollback_preview(snapshot_id, reason=reason)`; the SDK takes `limit` (client.py:935, max `MAX_DIFF_LIMIT` 500) |
| CLI `rollback preview` has no `--limit` | open | `cli/main.py:350-361` defines no `--limit`; line ~604 calls `rollback_preview(args.snapshot, reason=args.reason)` |
| No get-by-key | open | the SDK has `list_memories`, `iter_memories`, `history`, no single-key read |
| `if_absent` missing in SDK / Cloud MCP / CLI | open | `client.commit` (client.py:537-576) has no such parameter; only the private runtime/sidecar has it (`cloud/service.py:62`, `cloud/runtime.py:578`) |

## Scope decision: split B4
- **B4a (this item): rollback preview `limit` (Cloud MCP + CLI) and an SDK `get_memory`.** All of it is behaviour the SDK
  already has or can build from documented public calls.
- **B4b: `if_absent` over the public API is NOT done here; it goes to blocked-owner.** The SDK talks to the public
  `/api/cloud/memory/commit` of the control plane. The only evidence of `if_absent` in this repository is the private sidecar
  (snake_case `if_absent` on `/v1/projects/{id}/commit`); the public wire name (`ifAbsent`?), whether the control plane
  forwards it, and its error mapping for `memory_exists` are not documented in this repository (README lists no such field),
  and the control plane is not available to this session. A guessed field name against an older control plane would be
  ignored and the write would silently overwrite, which is exactly the failure the sidecar's own comment warns about
  (cloud/service.py:226-230). Needs the owner to confirm the contract (and that the control plane advertises the capability),
  after which the SDK can follow the existing `capability_unavailable` pattern used for list `order`/`sources`.

## B4a design

### 1. Rollback preview limit
- Cloud MCP `rollback` tool: add optional `limit: int = 100` (same default as the SDK and the diff tool), passed to
  `rollback_preview(..., limit=limit)` in preview mode. Ignored in execute mode (the execute call has no limit).
- CLI: `rollback --limit N` (default 100), passed in preview mode; execute ignores it and does not error.
- Validation stays in the SDK (`_require_limit`, 1..500), so an out-of-range value raises the same validation error as today.
- The confirmation token is bound to project, snapshot, state root and reason, not to the limit (client.py docstring), so
  changing the limit does not change which token is valid.

### 2. SDK `get_memory(key)`
Options: (a) a new public endpoint: not available (control plane out of scope, and no contract); (b) `list_memories(prefix=key,
limit=1, values="full")` and take the first row: wrong when ordering is not exact-key-first (collation) or other keys share
the prefix; (c) walk `iter_memories(prefix=key, values="full")` and return the first row whose `key` equals the requested key;
stop at the first match; raise `memory_not_found` if the walk ends without one. (c) is correct for any ordering and any prefix
semantics; its cost is the number of keys that share the prefix, which for real keys is small.
Chosen: (c). Signature `get_memory(key, *, values="full") -> dict`, returning the same entry dict the list returns (so it carries
`entryVersion`), raising `BilincNotFoundError` (`memory_not_found`, the existing code) when absent. The key is validated with the
existing `_require_key`. No new endpoint, no new wire field, nothing the service has to know about.
No new CLI command and no new MCP tool: list_memories with a key as `prefix` already covers those surfaces, and adding tools or
commands changes the published tool/command lists and the public docs, which is the owner's call.

## Test plan (tests first, `bilinc-test`)
- SDK transport tests (the existing fake-transport pattern in tests/test_cloud_memory_review_sdk.py): `rollback_preview` sends
  `limit`; MCP `rollback` preview passes `limit` through and defaults to 100; execute mode sends no limit; CLI
  `rollback preview --limit 7` sends 7, default sends 100, execute with `--limit` still works and ignores it; out-of-range
  limit (0, 501) raises the SDK validation error through MCP and CLI.
- MCP tool schema: `rollback.inputSchema.properties` contains `limit`, `required` is unchanged (`snapshot_id`, `reason`).
- `get_memory`: exact key found on page 1; found on a later page when other keys share the prefix and sort first (fake
  pages, incl. `"note"` listed after `"note-1"` to prove it does not rely on order); a longer key sharing the prefix is not
  returned; absent key raises `BilincNotFoundError` with `memory_not_found`; empty and over-long keys rejected by
  `_require_key`; `values` forwarded.
- Mutation check: dropping the `limit` pass-through in MCP and in CLI each fails its test; replacing the exact-key match with
  "first row" fails the later-page test.
- Public truth contract (`-m public_source`) stays green; README, server.json and tool lists are not edited.

## Release-chain impact
- PyPI package: changes (`client.py`, `cloud_mcp.py`, `cli/main.py` ship in the wheel). SDK, CLI and Cloud MCP adapter all
  change, additively: new optional parameters and one new SDK method; no existing call changes behaviour.
- MCP registry: the `rollback` tool input schema gains an optional `limit`; registry metadata is only touched by the version
  bump in the one synchronized release (`server.json` and `bilinc.__version__` must match, tests/test_public_truth_contract.py).
- Hosted runtime and site: no change. README/docs: the new options are not documented here (public text is the owner's call);
  CHANGELOG `[Unreleased]` entry in neutral wording.
- Migration: none; rollback is a revert. The version number is the owner's decision.
