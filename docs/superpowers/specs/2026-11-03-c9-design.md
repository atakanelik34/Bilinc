# C9: recall evidence reads only the newest 1000 claims, then filters by key in Python

## Problem
`StatePlane._recall_profile_evidence` (stateplane.py:1126-1138), used by the verified and deep recall profiles
(`include_claims: true`, stateplane.py:1077,1084), loads `list_claims(active=True, limit=1000)` and keeps the claims whose
`memory_key` is among the recalled results. Once a project holds more than 1000 active claims, the claims of a recalled
memory that are not among the 1000 newest are silently missing from `evidence.claims`, and the contradiction check
(`detect_claim_contradictions(selected)`) runs on that incomplete set, so a real contradiction can go unreported. No error
is raised. Today few projects have claims, so the practical impact is low, but the cut-off is arbitrary and invisible.

A keyed read already exists on both backends and is used by `_active_claims_by_memory_key` (stateplane.py:1149-1150):
`list_claims_for_memory_keys(keys, active=True)` (sqlite.py:795-814, postgres.py:883-906). Same filter (`active`,
`valid_at <= now`, `invalid_at > now`) and same order (`updated_at DESC`) as `list_claims`.

How the sites were found: `grep -rn "list_claims(" src/bilinc`. Remaining unkeyed 1000-row reads: this one,
`eval/contradictions.py:203` (an eval probe that also groups by subject across all claims, so a global read is part of
what it does; see "Out of scope") and the fallback at stateplane.py:1152 (only for a backend without the keyed method; none in
the tree).

## Approaches
1. Raise the limit (10000). Still arbitrary, loads the whole table into Python on every verified recall, gets slower as
   claims grow.
2. Ask the backend for exactly the recalled keys with `list_claims_for_memory_keys(sorted(keys), active=True)` and no
   row cap. The number of keys is bounded by the recall `limit` (a small caller-chosen number), each key's claims are
   few, and both backends filter in SQL (SQLite: `IN (...)`; Postgres: `= ANY($1)`).
3. Reuse `_active_claims_by_memory_key`. Rejected as is: it swallows every exception and returns `{}`, which would turn a
   database error into "no evidence" silently; the evidence block should keep failing loudly like today.

Chosen: 2, with the old path kept only as the fallback for a backend that lacks the keyed method (no such backend in the
tree; behaviour there is unchanged, still `limit=1000`). No empty-key query: with no recalled keys the backend is not
called and `claims` stays empty. Output shape, order (newest update first) and the contradiction step are unchanged.

## Test plan (tests first, `bilinc-test`)
- SQLite (always runs): a memory whose claim is older than 1100 newer claims of other keys. On origin/main the claim is
  missing from `evidence.claims` for the verified profile; with the fix it is present, and a contradiction between two of
  its claims is reported (it is missed today). Control: with few claims the output is identical before and after (same keys,
  same order).
- No recalled keys: backend method not called (stub backend counts calls); evidence is empty.
- Fallback: a backend stub without `list_claims_for_memory_keys` keeps using `list_claims`.
- An exception from the backend still propagates (not swallowed).
- Postgres test gated on `BILINC_TEST_POSTGRES_DSN`: same scenario through the hosted runtime (`manager.recall` with the
  verified profile), tenant schema, 1100 other claims written directly to `bilinc_claims`.
- Mutation check: reverting to the `limit=1000` read fails the SQLite and Postgres scenario tests.

## Out of scope
`eval/contradictions.py:203` (`probe_claim_contradictions_for_queries`) has the same 1000-row cap but groups claims by
subject across all keys on purpose; fixing it needs a design of its own. Proposed backlog item C9b (low, eval tooling,
not part of recall).

## Release-chain impact
- PyPI package: none (`core/` is pruned from the wheel and sdist, `MANIFEST.in`). SDK API: none. Site: none. MCP registry:
  version bump only as part of the one release. Migration: none; rollback is a revert.
- Hosted runtime: changes; ships only with the next synchronized version and its redeploy.
- Behaviour change: verified and deep recall may return more claims in `evidence.claims` (and report contradictions that
  were hidden) for projects with more than 1000 active claims; for smaller projects the output is identical.
- CHANGELOG `[Unreleased]` entry in neutral wording.
