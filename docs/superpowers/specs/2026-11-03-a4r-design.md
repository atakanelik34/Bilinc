# A4r: Postgres orphan entities and eval capture rows after forget and purge

## Problem
Two leaks keep text from a forgotten or purged memory in the store. Both were found by reading `origin/main` (5578d27).

**(a) Postgres never prunes orphan `entities`.**
- `PostgresBackend.delete` (`storage/postgres.py:1063-1076`) deletes the key's `entity_mentions` but never the `entities` those mentions pointed to.
- `delete_entity_mentions_for_memory_key` (`postgres.py:640-648`) has the same gap. There is no `DELETE FROM entities` anywhere in the file.
- `entities.canonical_name`, `aliases` and `metadata` come from the memory's value (`StatePlane._project_entities_for_entry`, `core/stateplane.py:655-695`). After a forget or purge they stay in the tenant schema.
- The gap is wider than forget. `_project_entities_for_entry` prunes only when the backend has `prune_orphan_entities` (`stateplane.py:667`). Postgres does not, so every rewrite of a memory that drops an entity also leaves an orphan.
- SQLite prunes on forget, on rewrite and with a one-time sweep (`storage/sqlite.py:299-303, 448-545`), so this is also a parity gap.

**(b) `eval_candidates` is skipped by purge, in both backends.**
- The hosted `_purge_key` (`cloud/runtime.py:1163-1196`) and the stdio `_purge_key_history` (`mcp_server/server_v2.py:1340-1362`) do not touch it.
- A capture row keeps the purged key name in `retrieved_keys`, `query` or `detail`, and may keep user-typed text that contained the purged value in `query` (`eval/capture.py:100-135`; table at `postgres.py:198-211`, `sqlite.py:152-166`). `scrub_query` removes secret-shaped strings only.
- Capture is gated by `BILINC_EVAL_CAPTURE` (`capture_enabled`, `eval/capture.py:38-46`). It is ON in the owner's local client configs since 2026-10-22. I could not confirm from here whether it is on for the hosted runtime.

## Approaches

### (a) Entities
1. **Port the SQLite pruning to `PostgresBackend` with the same method names and signatures (chosen).** The port covers every SQLite behaviour:
   - `entity_ids_for_memory_key`, `prune_orphan_entities`, `sweep_orphan_entities(older_than, dry_run)` (SQLite gains the same `dry_run` parameter, so the contract is one signature) and `delete_entity_mentions_for_memory_key(key, prune=True)`.
   - With `prune=False`, the touched entities get `updated_at` bumped to now (as in `sqlite.py:470-477`), so the age-guarded sweep spares entities that are being re-linked.
   - `save_entity_mention` prunes the old entity when a mention moves to another entity (as in `sqlite.py:606, 620-621`). The Postgres version today (`postgres.py:558-585`) overwrites `entity_id` and leaks the old entity.
   - `delete()` collects the touched entity ids and prunes them inside the same transaction as the mention delete.
   - `delete_entity_mentions_for_memory_key` (today a bare `pool.acquire()` with no transaction, `postgres.py:640-648`) runs the touched-id lookup, the mention delete and either the prune or the `updated_at` bump in one `conn.transaction()`. `save_entity_mention` does its upsert and the prune of the old entity on one connection in one `conn.transaction()`, so an error between the two statements cannot leave the old entity behind.
   - `StatePlane` needs no change: its `hasattr(self.backend, "prune_orphan_entities")` check then turns on the deferred prune for Postgres as well, which also fixes the rewrite leak.
   - Reason: one contract for both backends, the smallest diff, and the call sites already exist.
2. **Prune only in `delete()` and the purge path.** Smaller, but rewrites keep leaking and the two backends keep two contracts. Rejected.
3. **Foreign key with `ON DELETE CASCADE`, or a trigger.** Cleans without application code, but it changes the schema of every tenant under the per-schema migration lock, and a cascade cannot express "keep the entity while another memory still mentions it" without a trigger. Higher risk for the same result. Rejected.

**Existing tenants.** Pruning on future forgets does not remove orphans that already exist. Sweeping them is an explicit, opt-in operation, never part of `init()`.
- A new script, `scripts/sweep_pg_orphan_entities.py`, does the sweep. It is separate from `prewarm_pg_tenants.py`, whose non-dry run calls `backend.init()` on every tenant and so writes (migrations, full-text rebuild); this keeps `--dry-run` there unchanged.
- **Default (no flag): read-only.** It opens one plain connection, runs `SELECT COUNT(*)` of orphan entities per tenant schema, and prints one JSON line per schema. It never calls `init()` and writes nothing. A schema without an `entities` table is skipped and reported.
- **`--execute`** deletes over the same plain connection, never through `PostgresBackend`, so it does not run `init()` or any migration on a tenant. It uses schema-qualified, `quoted()` and `validate_schema_name()` identifiers as `prewarm_pg_tenants.py:26-53` does, and runs one age-guarded `DELETE FROM <schema>.entities WHERE updated_at < $1 AND NOT EXISTS (SELECT 1 FROM <schema>.entity_mentions m WHERE m.entity_id = entities.id)` per tenant. The statement is built by one function that takes the schema, used by both `PostgresBackend.sweep_orphan_entities` and the script, so the two cannot drift apart. The tests exercise that shared function.
- The age guard and the idempotence below apply to `--execute`.
- `init()` and normal traffic never delete a pre-existing orphan. Only rows touched by a forget, a rewrite or a mention move are pruned from now on, so no production row disappears without the owner running the sweep.
- The sweep is age-guarded (`updated_at` older than `ORPHAN_SWEEP_MIN_AGE_SECONDS`, 3600 s, as in SQLite), so an entity another writer is about to link is kept.
- The sweep is idempotent, so it needs no run-once marker. This avoids a new `maintenance` table: **there is no schema change** (the SQLite `maintenance` table is not ported, and `TENANT_TABLES` stays as it is). An older runtime after a downgrade ignores all of this. Orphans it creates can be cleared by running the sweep again.
- A sweep removes derived rows only: an orphan has no mention, so nothing in recall reads it.

### (b) Capture rows
1. **Delete the capture rows whose `retrieved_keys` contains the purged key, in both backends (chosen).** New `purge_eval_candidates(memory_key) -> int` on each backend, called from `_purge_key` and `_purge_key_history` next to `purge_memory_event_payloads`.
   - `StatePlane.recall(key=...)` writes a capture row with `query=key` and `detail={"key": key, ...}` (`core/stateplane.py:717-723`). After a forget this is the common case: someone recalls the key to check it is gone, `retrieved_keys` is empty, and only `query` and `detail.key` hold the name. The delete therefore matches a row when `retrieved_keys` lists the key, or `query` equals it, or `detail.key` equals it.
   - The stored entry is `scrub_query(key)` (`eval/capture.py`, `row_from_results`), which can differ from the raw key when it holds a secret-shaped substring or is long. The delete therefore matches both the raw key and `scrub_query(key)`.
   - Postgres: `DELETE FROM eval_candidates WHERE retrieved_keys @> to_jsonb($1::text) OR retrieved_keys @> to_jsonb($2::text) OR query IN ($1, $2) OR detail->>'key' IN ($1, $2)`.
   - SQLite: `DELETE ... WHERE query IN (?, ?) OR (json_valid(retrieved_keys) AND EXISTS (SELECT 1 FROM json_each(retrieved_keys) WHERE value IN (?, ?))) OR (json_valid(detail) AND json_extract(detail, '$.key') IN (?, ?))`. The `json_valid` guards keep a malformed row from aborting the statement.
   - Order: `purge_eval_candidates` runs FIRST in both `_purge_key` (`cloud/runtime.py`) and `_purge_key_history` (`server_v2.py`), before `audit.purge_key`, and so also before `compact_search_index` (the SQLite compaction is what clears the old pages). Reason: the retry gates. After a forget has committed, `_handle_forget` (`server_v2.py:1316-1321`) admits a purge only if a stored row or belief exists, or `audit.has_purgeable_rows(key)`, or `has_unpurged_memory_events(key)` is true (the hosted `forget`, `cloud/runtime.py:1105-1108`, differs: it checks only `audit.has_purgeable_rows` and the snapshots, not the events, so a hosted retry is admitted only while audit is enabled; the hosted plane sets `audit_enabled = True` for both backends, `runtime.py:500-503`, and the hosted case of test 9 runs with audit on). If the capture delete ran after the audit and event purges and failed, those gates would be false and the retry would return `memory_not_found`, leaving the capture rows. Running it first means a failure leaves purgeable audit rows, so the existing gate admits the retry. The other option, adding a "capture rows still name this key" check to both gates, is a larger change to two admission paths and is not chosen.
   - The purge result dicts keep their current keys (`audit_rows`, `events`, `snapshots`, `wal_checkpointed`); the deleted-row count is not added, so no SDK or site change follows.
   - If the capture delete raises, the purge fails closed and does not report success, because a partial purge must not look complete. The forget itself is already committed by then, so the error says so.
     - stdio: `_handle_forget` returns an error in the existing shape `{"success": false, "error": "purge_incomplete", "detail": "..."}` (the shape used at `server_v2.py:1308, 1321`). **`purge_incomplete` is a new code** (it appears nowhere in the repo today), so it is added to the CHANGELOG. The SDK's code table (`client.py:54-57`) covers hosted codes only and needs no change. The detail says the memory was forgotten but the purge did not finish and should be retried. No `purged` key is returned.
     - Hosted: a non-`ValueError` raised by the capture delete is not swallowed and escapes `_runtime_errors` (`cloud/service.py:186-197`) as a plain 500 from the sidecar. This is the same behaviour as any other unexpected purge-step failure today. No public error code is added, so `_PUBLIC_RUNTIME_ERRORS` and the site are untouched.
     - A retry of the purge is idempotent (every step deletes by key) and, with the order above, is admitted by the retry gates and completes the cleanup.

2. **Redact in place:** replace the key in `query` and `detail`, and drop it from `retrieved_keys`, keeping the row. This preserves eval data, but `retrieved_scores` and `memory_types` are parallel arrays, so dropping one key misaligns them unless all three are rewritten together; and a redacted `query` is no longer the query that was asked, so it is poor evidence for the L4/B1 retune anyway. Rejected.
3. **Match the purged value's text in `query`.** Rejected: after the forget the value is gone, and matching text would need fuzzy substring search with no stable normalisation and a risk of deleting unrelated rows.
4. **A bounded exact match** (capture the scrubbed value before the forget and delete rows whose `query` equals it). Not chosen: it needs the value at purge time on both paths, adds a write path for a rare case, and still misses rephrased queries.

**Why delete is acceptable.** The rows deleted are only those that name the purged key. They are measurement samples for the later retune (L4, B1), not user memory. Losing the few rows that involve a key the user asked to remove costs a small amount of eval data, and a trace of the removed key is worse than that loss.

**Known limit (kept in the ready note and the release note).** A capture row whose `query` holds the purged value but never retrieved, named or recalled the key stays: for example a search typed before the memory was written, or one where the key ranked outside the stored results. The purge removes rows that **name the key** (`retrieved_keys`, `query == key`, `detail.key`); it does not claim to remove every capture query that quoted the value. The public wording therefore stays "removed from storage and history" and must not be read as covering capture queries. Capture is opt-in (`BILINC_EVAL_CAPTURE`), and the owner can clear the capture table through the eval tooling.

A plain forget (not a purge) leaves capture rows alone; only entity pruning applies to it.

## Concurrency
`entity_mentions.entity_id` has no foreign key, and `StatePlane` commits `save_entity` and `save_entity_mention` as separate statements.
- **The only guarantee is the per-project mutation lock** (`cloud/runtime.py:447`, `_serialized_project_mutation`): a forget, a rewrite and a purge on one project never interleave inside one worker. `_project_entities_for_entry` also prunes only after saving the new mentions.
- The targeted prune matches SQLite exactly: `DELETE FROM entities WHERE id = ANY($1) AND NOT EXISTS (SELECT 1 FROM entity_mentions m WHERE m.entity_id = entities.id)`. It has **no recency skip**: a recency guard would skip every entity the rewrite path has just touched (`prune=False` bumps `updated_at`, then the prune runs milliseconds later) and a forget soon after a write, which would leave the leak open.
- Only `sweep_orphan_entities` keeps the 3600 s age guard, as in SQLite, because it scans all tenants' rows while other writers may be linking.
- A row lock (`FOR UPDATE`) is not used: a concurrent mention `INSERT` takes no lock on the `entities` row, so it would not block the race and would only look like a protection.
- Limit, stated in a code comment: a second worker process is outside this guarantee, as for the audit chain head (backlog A8a).

## Test plan (tests first, small commits)
Postgres tests run under the DSN gate; SQLite tests run always.
1. Forget a memory whose entity is mentioned only by it, immediately after writing it with no sleep: no `entities` row remains. An entity another memory still mentions stays, with its aliases and metadata.
2. Rewrite a memory so it no longer mentions an entity (Postgres), immediately after the first write with no sleep: the orphan is pruned. A rewrite that keeps the entity keeps its aliases and metadata.
3. A mention moves to another entity (Postgres `save_entity_mention`): the old entity is pruned if it has no other mention.
4. `delete_entity_mentions_for_memory_key(prune=False)` bumps `updated_at` on the touched entities and prunes none.
5. Purge a key: no row in `entities`, `entity_mentions` or `memory_events` contains the purged value's text, and no row in `eval_candidates` names the key, whether in `retrieved_keys`, `query` or `detail.key`. This includes a `recall(key)` that found nothing and was captured before the purge.
6. `init()` deletes no pre-existing orphan. `sweep_orphan_entities(dry_run=True)` deletes nothing and returns the count, on both backends. The execute form deletes old orphans and spares a recent one (age guard). Running it twice is safe.
7. `scripts/sweep_pg_orphan_entities.py`: without `--execute` it changes nothing. The test records `schema_version` and the row counts of `entities` and `entity_mentions` before and after, and asserts no `init()` ran. A schema without an `entities` table is skipped and reported. With `--execute` it deletes the old orphans.
8. Known limit, negative test: a capture row whose `query` holds the purged value but never named the key stays after the purge, and the test comment points to the documented limit.
8b. `purge_eval_candidates`: removes rows listing the key, leaves other rows, in both backends. Includes a secret-shaped key whose stored form is `scrub_query(key)`, and a malformed `retrieved_keys` row on SQLite that must not abort the delete.
9. Failure: if `purge_eval_candidates` raises, both the hosted path and the stdio path return the error shapes above and no `purged` block. A retry after the forget is committed, with no snapshot holding the key, is admitted and leaves no trace, on SQLite and on Postgres.
10. Parity: the same scenario gives the same result on SQLite and Postgres.
- A test records call order and asserts `purge_eval_candidates` runs before `audit.purge_key` and `compact_search_index`.
- Run through `bilinc-test` only: `-q -m public_source`, `-q -m internal_runtime`, the Postgres tests, and `.venv/bin/ruff check`.

## Rollback and who runs what
- Code: revert the commit. No schema change and no new column.
- Per-write pruning only removes rows that a forget, rewrite or mention move has just orphaned. Capture rows are removed only on a purge of their key.
- The sweep script (`--execute`) removes pre-existing rows for good. The way back is the count-only run first, and the nightly off-site backup. I could not verify from here that the backup covers the tenant schemas, so the owner confirms that before running `sweep_pg_orphan_entities.py --execute`.
- **Running the sweep in production is an owner step. The worker ships the code and tests only.** Nothing here touches a production database or the owner's local `~/bilinc.db`.

## Release-chain impact
- **Surfaces whose behaviour changes:** the runtime and the PyPI package only: both storage backends, the two purge paths and a new sweep script. No API, tool schema or response field changes (the purge result keys stay the same), so SDK behaviour, site code and the MCP tool list do not change. The new stdio error code `purge_incomplete` goes into the CHANGELOG.
- **Artifacts whose version moves with the release:** `pyproject.toml`, `bilinc.__version__`, `server.json` (two pins) and the MCP registry entry, the hosted runtime image, and any site version display. `tests/test_public_truth_contract.py:12-17` requires `server.json`, pyproject and `bilinc.__version__` to share one version, so any new PyPI version also needs a `server.json` bump and a registry publish in the same release. All of these ship together at the version the owner chooses (the backlog already reserves a later release for the fusion retune).
- **Migration:** none. No schema change; the sweep is a separate owner-run command.
- **Public text:** the known limit on capture queries applies; nothing may claim a purge removes "everything" without this fix. The owner's wording rule stays: "removed from storage and history".
