# A4r: Postgres orphan entities and eval capture rows after forget and purge

## Problem
Two leaks keep text from a forgotten or purged memory in the store. Both were found by reading `origin/main` (5578d27).

**(a) Postgres never prunes orphan `entities`.**
- `PostgresBackend.delete` (`storage/postgres.py:1063-1076`) deletes the key's `entity_mentions` but never the `entities` those mentions pointed to.
- `delete_entity_mentions_for_memory_key` (`postgres.py:640-648`) has the same gap. There is no `DELETE FROM entities` anywhere in the file.
- `entities.canonical_name`, `aliases` and `metadata` come from the memory's value (`StatePlane._project_entities_for_entry`, `core/stateplane.py:655-695`). After a forget or purge they stay in the tenant schema.
- The gap is wider than forget. `_project_entities_for_entry` prunes only when the backend has `prune_orphan_entities` (`stateplane.py:667`). Postgres does not, so every rewrite of a memory that drops an entity also leaves an orphan.
- SQLite prunes on forget, on rewrite and with a one-time sweep (`storage/sqlite.py:299-303, 448-545`), so this is also a parity gap.

**(b) `eval_candidates` is skipped by purge, in both backends.**
- The hosted `_purge_key` (`cloud/runtime.py:1163-1196`) and the stdio `_purge_key_history` (`mcp_server/server_v2.py:1340-1362`) do not touch it.
- A capture row keeps the purged key name in `retrieved_keys` and may keep user-typed text that contained the purged value in `query` and `detail` (`eval/capture.py:100-135`; table at `postgres.py:198-211`, `sqlite.py:152-166`). `scrub_query` removes secret-shaped strings only.
- Capture is gated by `BILINC_EVAL_CAPTURE` (`capture_enabled`, `eval/capture.py:38-46`). It is ON in the owner's local client configs since 2026-10-22. I could not confirm from here whether it is on for the hosted runtime.

## Approaches

### (a) Entities
1. **Port the SQLite pruning to `PostgresBackend` with the same method names and signatures (chosen).**
   - Add `entity_ids_for_memory_key`, `prune_orphan_entities`, `sweep_orphan_entities` and `delete_entity_mentions_for_memory_key(key, prune=True)`.
   - `delete()` collects the touched entity ids and prunes them inside the same transaction as the mention delete.
   - `StatePlane` needs no change: its `hasattr(self.backend, "prune_orphan_entities")` check then turns on the deferred prune for Postgres as well, which also fixes the rewrite leak.
   - Reason: one contract for both backends, the smallest diff, and the call sites already exist.
2. **Prune only in `delete()` and the purge path.** Smaller, but rewrites keep leaking and the two backends keep two contracts. Rejected.
3. **Foreign key with `ON DELETE CASCADE`, or a trigger.** Cleans without application code, but it changes the schema of every tenant under the per-schema migration lock, and a cascade cannot express "keep the entity while another memory still mentions it" without a trigger. Higher risk for the same result. Rejected.

**Existing tenants.** Pruning on future forgets does not remove orphans that already exist.
- Run a one-time sweep when a tenant schema is first opened after the deploy, the same pattern as SQLite: a `maintenance` row named `orphan_entity_sweep`, taken under the existing migration advisory lock (`postgres.py:360-377`).
- The sweep is age-guarded (`updated_at` older than `ORPHAN_SWEEP_MIN_AGE_SECONDS`, 3600 s, as in SQLite) so an entity another writer is about to link is kept.
- `sweep_orphan_entities(dry_run=True)` returns the count without deleting. The prewarm script can log it first.
- It removes derived rows only: an orphan has no mention, so nothing in recall reads it.

### (b) Capture rows
1. **Delete the capture rows whose `retrieved_keys` contains the purged key, in both backends (chosen).** New `purge_eval_candidates(memory_key) -> int` on each backend, called from `_purge_key` and `_purge_key_history` next to `purge_memory_event_payloads`.
   - Postgres: `DELETE FROM eval_candidates WHERE retrieved_keys @> to_jsonb($1::text)`.
   - SQLite: `DELETE ... WHERE EXISTS (SELECT 1 FROM json_each(retrieved_keys) WHERE value = ?)`.
   - Reason: scores and memory types are positional arrays, so removing one key from `retrieved_keys` would misalign them. The rows are measurement data, not user memory, and losing a few is cheaper than keeping a trace.
2. **Remove only the key from the arrays.** Keeps the row but misaligns the parallel arrays. Rejected.
3. **Match purged text in `query`.** A purge call knows the key, not the value, once the value is gone, so this cannot be done reliably. Not attempted. This stays a documented limit: a user-typed query that quoted a purged value is not found by key. The mitigation is that capture is opt-in and the rows can be deleted by the owner through the eval tooling.

A plain forget (not a purge) leaves capture rows alone; only entity pruning applies to it.

## Concurrency
`prune_orphan_entities` deletes only ids that have no mention at that moment. `entity_mentions.entity_id` has no foreign key, so a mention inserted between the check and the delete could point to a deleted entity. The hosted runtime serializes mutations per project (`cloud/runtime.py:447`, `_serialized_project_mutation`), and `_project_entities_for_entry` already prunes only after saving the new mentions. The sweep's age guard covers the multi-process case, as in SQLite. I will state this limit in the code comment.

## Test plan (tests first, small commits)
Postgres tests run under the DSN gate; SQLite tests run always.
1. Forget a memory whose entity is mentioned only by it: no `entities` row remains. The entity another memory still mentions stays, with its aliases and metadata.
2. Rewrite a memory so it no longer mentions an entity (Postgres): the orphan is pruned. A rewrite that keeps the entity keeps its aliases and metadata.
3. Purge a key: no row in `entities`, `entity_mentions`, `memory_events` or `eval_candidates` contains the purged value's text or lists the key.
4. One-time sweep: pre-existing orphans are removed once, a recent orphan survives (age guard), the `maintenance` row stops a second sweep, `dry_run=True` deletes nothing and returns the count.
5. `purge_eval_candidates`: removes rows listing the key, leaves other rows, in both backends. Capture rows are created through the existing `record_eval_candidate`.
6. Parity check: the same scenario gives the same result on SQLite and Postgres.
- Run through `bilinc-test` only: `-q -m public_source`, `-q -m internal_runtime`, the Postgres tests, and `.venv/bin/ruff check`.

## Rollback and who runs what
- Code: revert the commit. No schema change, no new column.
- Data: the sweep and the capture deletes remove rows for good. The way back is the nightly off-site backup and the `dry_run` count taken first. I could not verify from here that the backup covers the tenant schemas, so the owner should confirm it before the sweep runs in production.
- **Running the sweep in production is an owner step at release. The worker ships the code and tests only.** Nothing here touches a production database or the owner's local `~/bilinc.db`.

## Release-chain impact
- **Runtime and PyPI package:** yes, both backends and the two purge paths change. A patch release (2.6.1) is suggested for the owner to decide.
- **SDK surface, site, MCP registry:** none. No public API, tool schema or response field changes.
- **Migration:** no schema migration. One data sweep per tenant on first open, described above.
- **Public text:** nothing may claim a purge removes "everything" without this fix. The owner's wording rule stays: "removed from storage and history".
