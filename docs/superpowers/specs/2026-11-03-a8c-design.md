# A8c: hosted purge leaves purged values in the AGM revision log, and the log is unbounded

## Problem
Every AGM operation appends an `AGMResult` to `AGMEngine.operation_log` (`adaptive/agm_engine.py:116, 297, 365, 413, 524, 740`). A revision result carries `new_beliefs`, a dict of the `MemoryEntry` objects, values included, and an explanation trail. The list lives as long as the process.

- **Purge does not clear it on the hosted path.** `redact_operation_log` (`agm_engine.py:744-762`) drops the records that mention a key. Its only caller is the local stdio purge (`mcp_server/server_v2.py:1354-1356`, added by `18ef1c7`). The hosted `_purge_key` (`cloud/runtime.py:1163-1196`) never calls it, so after a hosted purge the purged text stays in process memory, through the revisions of that key, until the runtime restarts. The hosted plane keeps one AGM engine for the life of the project plane, and planes are not evicted (backlog item A8b), so that can be a long time.
- **The list is unbounded.** Nothing trims it. A busy project grows it with every write, and each record holds full entries.

The KG half of the old finding is already closed (`StatePlane.forget` -> `graph.forget_memory`, `core/stateplane.py:3298-3302`).

## Approaches
1. **Call `redact_operation_log` from the hosted purge, and cap the log (chosen).**
   - In `_purge_key` the call sits with the other in-process steps, so the hosted and stdio purges clear the same things.
   - The log keeps only the newest `max_operation_log` records (default 1000, a constructor argument of `AGMEngine`; the trim is done in one place, a `_record` method every append goes through). The log is a debugging and explanation aid, not storage: the audit trail and the event ledger are the history.
   - The cap would make `len(operation_log)` plateau, and two status outputs report it as "operations" (`server_v2.py:1521`, `core/stateplane.py:3619`). A counter `operations_total` (never trimmed) feeds those two numbers, so the reported count does not change meaning.
2. **Redact on every forget, not only on purge.** Rejected: a plain forget keeps its audit trail and history on purpose (the audit rows hold the values for `history` and rollback), so wiping the in-memory log on forget would make the stdio and hosted paths differ from what plain forget promises everywhere else. Purge is the operation that promises removal.
3. **Replace the list with a `collections.deque(maxlen=...)`.** Bounded for free, but `server_v2.py:1643` slices the log (`operation_log[-50:]`) and `redact_operation_log` assigns into it (`log[:] = kept`); a deque supports neither. Changing both call sites for the same effect is the larger diff. Rejected.

## Concurrency
`purge` runs under the per-project mutation lock (`_serialized_project_mutation`), and the AGM operations that append to the log run under the same lock on the hosted path, so the redaction does not race an append inside one worker. A second worker process has its own engine and its own log; that is outside the single-worker design (backlog A8a).

## Test plan (tests first, small commits)
Hosted runtime on SQLite, and on Postgres when `BILINC_TEST_POSTGRES_DSN` is set (the log is in memory, so the storage backend only changes which purge runs).
1. Commit a key, revise it twice with distinct texts, then purge it through the hosted manager: no record in `plane.agm_engine.operation_log` names the key or holds one of the texts (check `repr` of the whole log); records of another key survive.
2. The stdio path still does the same (existing coverage in `tests/test_forget_state_sync.py` and `tests/test_purge.py` stays green).
3. Cap: with `max_operation_log=5`, run more than 5 operations; the log holds the newest 5, `operations_total` counts all, and the two status outputs report the total.
4. Default: an `AGMEngine()` keeps 1000 records and trims after that; `max_operation_log=None` leaves the log unbounded (for callers that want the old behaviour).
5. A purge of a key with no records returns without error.
6. Run through `bilinc-test` only: `-q -m public_source`, `-q -m internal_runtime`, the Postgres tests, and `.venv/bin/ruff check`.

## Rollback and who runs what
- Code: revert the commit. No schema change, no data change, nothing to run in production.
- The only visible difference: the revision log of a long-running plane holds at most 1000 records, and the `operations` figure still counts every operation.
