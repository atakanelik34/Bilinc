# A8a: Postgres audit and event chain heads are read without a lock

## Problem
Each append to a hash chain reads the current head and inserts the next row inside one transaction, but nothing stops
two transactions from reading the same head. Under READ COMMITTED both then insert a row whose `prev_root` /
`prev_event_hash` is the same old head: the chain forks, and `verify_chain` (audit) or the event-chain check fails for
good. Sites (all on origin/main 5578d27):

| Chain | Site | Used by |
|---|---|---|
| `audit_log` (`root_hash`) | `core/postgres_audit_sync.py:96` | hosted runtime (`stateplane.py:299-302`) |
| `audit_log` | `core/postgres_audit.py:74` | async twin, no caller in `src/` today (kept consistent) |
| `memory_events` (`event_hash`) | `storage/postgres.py:419-422` (`ORDER BY time DESC, id DESC`) | hosted event ledger |

Today this is latent: one worker per process and a per-project mutation lock in `ProjectRuntimeManager`
(`cloud/runtime.py:49`, applied to the mutating methods) serialize the writers of one project. It stops holding as soon as
a second worker, a second replica, a script or a maintenance job writes to the same tenant schema, and the lock lives in
process memory only. The local SQLite audit already closes the same gap with `BEGIN IMMEDIATE`
(`core/audit.py:197`); Postgres has no equivalent. (SQLite `memory_events`, sqlite.py:889, runs under the same
single-writer file lock and is out of scope.)

How the sites were found: `grep -rn "DESC LIMIT 1\|FOR UPDATE\|pg_advisory" src/bilinc`; every chain-head read in the
Postgres code is in the table, the other hits are `schema_version` reads.

## Approaches
1. Document "single worker only". Cheapest, but the guarantee is then a deployment convention that fails silently into a
   corrupted audit chain, the one thing the audit trail exists to prevent.
2. Transaction-scoped advisory lock taken at the start of the append transaction:
   `SELECT pg_advisory_xact_lock(hashtextextended(current_schema() || ':audit_log', 0))` (and `':memory_events'` for the
   event chain). One lock per tenant schema and chain, released automatically at commit or rollback, no schema change, no
   migration, works on an empty table. Cost: appends of one chain serialize in the database (they already serialize in the
   process).
3. `SELECT ... FOR UPDATE` on the last row, or `SERIALIZABLE` with retry. `FOR UPDATE` with `ORDER BY ... LIMIT 1` can
   return a stale head after the wait under READ COMMITTED and does nothing on an empty chain; `SERIALIZABLE` needs
   retry loops at every caller. A `UNIQUE (prev_root)` index would reject the fork but needs a migration and cannot be
   created on a table that already forked.

Chosen: 2. The lock key is derived from `current_schema()`, so it follows the connection's `search_path` (tenant schema or
`public`), not a name passed by the caller. The audit and event chains use different keys, so they do not block each
other. The existing in-process mutation lock stays; this is the second, cross-process layer.

Placement: the lock statement is the first statement of the transaction, before the head read, in all three sites. The
event timestamp (`create_memory_event`) is already created after the read, inside the transaction, so with the lock the
`ORDER BY time DESC, id DESC` head is the last committed event. The audit `timestamp` and `data_hash` computed before
the lock do not enter the chain link (`prev_root` comes from the locked read); they stay as they are.

## Test plan (tests first, `bilinc-test`, Postgres tests gated on `BILINC_TEST_POSTGRES_DSN`)
- Lock is taken: a second connection holds `pg_advisory_xact_lock` for the same key inside an open transaction; an append
  on each of the three sites must still be pending after a short wait (`asyncio.wait_for` / thread join timeout) and
  complete after the holder commits; an append on the other chain (other key) is not blocked. Deterministic.
- Concurrency: 25 concurrent appends per site (asyncio gather for the async sites, threads for the sync trail) into one
  tenant schema, then assert: no two rows share a `prev_root` / `prev_event_hash`, each `prev` equals the previous
  row's hash, `verify_chain` reports valid (events: the existing chain verification).
- Red first: on origin/main the concurrency test fails (fork) and the lock test fails (no wait); I record how often the
  fork shows up in 5 runs and do not claim a rate.
- Mutation check: removing the lock statement from each site fails that site's lock test.
- Tenant isolation: a lock held for schema A does not block an append in schema B.

## Release-chain impact
- PyPI package: none of the changed files ship in the wheel (`core/postgres_audit*.py` and `storage/` are pruned,
  `docs/repository-contract.md:13`); I verified this by reading `MANIFEST.in` and the package list, not by building an
  sdist (no build backend in this venv).
- Hosted runtime: changes; Cloud gets it with a runtime redeploy. No SDK, site or MCP-registry change.
- Migration: none (no schema or data change). Rollback: revert the code; advisory locks leave no state.
- Performance: one extra round trip per audit or event append, serialized per tenant and chain; no measurement
  claimed.
- CHANGELOG `[Unreleased]` entry in neutral wording (no deploy internals).
