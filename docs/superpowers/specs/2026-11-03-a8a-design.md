# A8a: Postgres audit and event chain heads are read without a lock

## Problem
Each append to a hash chain reads the current head and inserts the next row inside one transaction, but nothing stops
two transactions from reading the same head. Under READ COMMITTED both then insert a row whose `prev_root` /
`prev_event_hash` is the same old head: the chain forks, and `verify_chain` (audit) or the event-chain check fails for
good. Sites (all on origin/main 5578d27):

| Chain | Site | Used by |
|---|---|---|
| `audit_log` (`root_hash`) | `core/postgres_audit_sync.py:96` | hosted runtime (`stateplane.py:299-302`) |
| `audit_log` | `core/postgres_audit.py:74` | async twin, no caller in `src/` today (kept consistent) |
| `memory_events` (`event_hash`) | `storage/postgres.py:419-422` (`ORDER BY time DESC, id DESC`) | hosted event ledger |

Today this is latent: one worker per process and a per-project mutation lock in `ProjectRuntimeManager`
(`cloud/runtime.py:49`, applied to the mutating methods) serialize the writers of one project. It stops holding as soon as
a second worker, a second replica, a script or a maintenance job writes to the same tenant schema, and the lock lives in
process memory only. The local SQLite audit already closes the same gap with `BEGIN IMMEDIATE`
(`core/audit.py:197`); Postgres has no equivalent. (SQLite `memory_events`, sqlite.py:889, runs under the same
single-writer file lock and is out of scope.)

How the sites were found: `grep -rn "DESC LIMIT 1\|FOR UPDATE\|pg_advisory" src/bilinc`; every chain-head read in the
Postgres code is in the table, the other hits are `schema_version` reads.

## Approaches
1. Document "single worker only". Cheapest, but the guarantee is then a deployment convention that fails silently into a
   corrupted audit chain, the one thing the audit trail exists to prevent.
2. Transaction-scoped advisory lock taken at the start of the append transaction:
   `SELECT pg_advisory_xact_lock(hashtextextended('bilinc_chain:audit_log:' || current_schema(), 0))` (and
   `'bilinc_chain:memory_events:'` for the event chain; same prefix style as the migration lock at `postgres.py:360`;
   `hashtextextended` needs PostgreSQL 11 or newer, and the hosted runtime and the test database are newer). One lock per tenant schema and chain, released automatically at commit or rollback, no schema change, no
   migration, works on an empty table. Cost: appends of one chain serialize in the database (they already serialize in the
   process).
3. `SELECT ... FOR UPDATE` on the last row, or `SERIALIZABLE` with retry. `FOR UPDATE` with `ORDER BY ... LIMIT 1` can
   return a stale head after the wait under READ COMMITTED and does nothing on an empty chain; `SERIALIZABLE` needs
   retry loops at every caller. A `UNIQUE (prev_root)` index would reject the fork but needs a migration and cannot be
   created on a table that already forked.

Chosen: 2. The lock key is derived from `current_schema()`, so it follows the connection's `search_path` (tenant schema or
`public`), not a name passed by the caller. The audit and event chains use different keys, so they do not block each
other. The existing in-process mutation lock stays; this is the second, cross-process layer.

Placement: `SET LOCAL lock_timeout = '10s'` and then the lock statement are the first statements of the transaction, before the head read, in all three sites. The timeout matters because the sync trail is a blocking call made from async code: a second writer stuck idle in a transaction must fail the append (lock_not_available), not freeze the process's event loop. The failed append rolls back like any other error; a test pins it (see failure paths). The
audit `timestamp` and `data_hash` computed before the lock do not enter the chain link (`prev_root` comes from the locked
read); they stay as they are.

### Event chain order (found by the design gate)
The event head is read with `ORDER BY time DESC, id DESC`, but `time` is the writer's wall clock
(`event_ledger.py:169`) and `id` is a random `evt_<uuid4>`. A second writer (the case this item is about) can have a skewed
clock, and even one machine's clock can step back, so under the lock a later append could carry a smaller `time`, the next
append would then read an older row as head and fork the chain anyway. Options without a migration: (a) read the head
by `time` as today and make `time` strictly increasing per chain under the lock; (b) add a sequence column (migration,
rejected). Chosen (a): the head select also returns `time`, and the new event is created with
`created_at = max(time.time(), previous_time + 1e-6)` (1e-6 is above the float resolution at epoch ~1.8e9, about 2.4e-7).
Every new event then has a strictly greater `time` than the head it links to, so the max-`time` row is always the last
appended one, whatever the clock does; the `id` tie-break never decides. The hashed `time` can differ from the wall
clock by the skew; that is the price of a linear chain and is documented in the CHANGELOG entry. Rows written before this
change are untouched. The audit chain is ordered by the `BIGSERIAL` id, so it needs no such rule.

## Test plan (tests first, `bilinc-test`, Postgres tests gated on `BILINC_TEST_POSTGRES_DSN`)
- Lock is taken: a second connection holds the advisory lock for the same key inside an open transaction; an append
  on each of the three sites must still be pending after a short wait (`asyncio.wait_for` / thread join timeout) and `pg_locks` must show it waiting
  (`locktype = 'advisory' AND NOT granted`), so the test does not rest on timing alone; it completes after the holder commits; an append on the other chain (other key) is not blocked. Deterministic. A lock held
  for tenant schema A does not block an append in schema B.
- Concurrency, with truly independent writers: every writer has its own connection to the same tenant schema (sync
  trail: one `SyncPostgresAuditTrail` instance per thread; async trail and event ledger: one backend instance with its own
  pool per task, not one shared pool), 25 appends per site. The sync trail is never shared between threads.
  Audit assertions: no two rows share a `prev_root`, each `prev_root` equals the previous row's `root_hash`, and
  `verify_chain` reports valid. Event assertions (there is no event-chain verifier in `src/`, so the test walks the chain
  itself): the walk starts at the row whose `prev_event_hash` is `None` and follows `event_hash` -> `prev_event_hash` links
  (independent of `time`); all 25xN rows must be reached and the walk must end at the max-`time` row; each `prev_event_hash` equals the previous row's
  `event_hash`; no `prev_event_hash` appears twice; one head; every `event_hash` equals `compute_event_hash` of the
  stored row.
- Clock steps back: with `time.time` monkeypatched to return a smaller value for the second of two consecutive event
  appends, the chain stays linear and `time` is strictly increasing.
- Lock timeout: with a second connection holding the lock and `lock_timeout` set low through a module constant patched in the test, the append raises and the chain did not advance.
- Failure paths: an exception injected after the lock and before the INSERT rolls back, the next append is not blocked
  and the chain did not advance; a connection that holds the lock and is closed releases it (the next append proceeds).
- SQLite unchanged: the existing SQLite audit and event tests stay green in `-m internal_runtime`.
- Red first: on origin/main the concurrency and lock tests fail; I record how often the fork shows in 5 runs and claim
  no rate. Mutation check: removing the lock statement at each site fails that site's lock test; removing the `max(...)`
  rule fails the clock test.

## Known limit (not fixed here)
`get_root_hash()` returns a process-local cached `_root_hash`, which `state_version` (`runtime.py:172-176`) and the rollback
confirmation binding (`runtime.py:1408-1430`) use. With a second writer that cache can be stale. The lock prevents forks
of the chain; it does not make multi-writer use supported, and nothing here claims a second replica is safe. Follow-up
backlog item proposed: A8d, read the chain head from the database where those two callers need it.

## Release-chain impact
- PyPI package: none of the changed files ship in the wheel (`core/postgres_audit*.py` and `storage/` are pruned,
  `docs/repository-contract.md:13`); I verified this by reading `MANIFEST.in` and the package list, not by building an
  sdist (no build backend in this venv).
- Hosted runtime: changes; ships only with the next synchronized version and its runtime redeploy (CHANGELOG `[Unreleased]`), not as a separate redeploy. No SDK, site or MCP-registry change.
- Migration: none (no schema or data change). Rollback: revert the code; advisory locks leave no state.
- Performance: one extra round trip per audit or event append, serialized per tenant and chain; no measurement
  claimed.
- CHANGELOG `[Unreleased]` entry in neutral wording (no deploy internals).
