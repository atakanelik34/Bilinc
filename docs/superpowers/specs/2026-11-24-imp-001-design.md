# IMP-001: a hosted revise records the memory's real previous state

Date: 2026-11-24. Branch `vm/imp-001` from origin/main `29ed56d` (2.7.3). Source: improve plan
`state/improve-2026-11-10/001-revise-audit-before-state.md` (written at 085bb99); every line below was
re-read on 29ed56d.

## Problem

`ProjectRuntimeManager._revise_loaded` (src/bilinc/cloud/runtime.py:1213-1320) takes
`previous_state`, the stored row as a dict (version-checked by the caller), and builds two entries
from shallow copies of it:

- runtime.py:1248 `plane.agm_engine.belief_state.add_belief(MemoryEntry.from_dict(dict(previous_state)))`
- runtime.py:1252 `entry_data = dict(previous_state)` ... `entry = MemoryEntry.from_dict(entry_data)`

`dict(...)` copies only the top level, and `MemoryEntry.__post_init__` keeps the same `metadata`
object when there is no reserved key to strip (core/models.py:127-138, 170-172). So
`previous_state["metadata"]`, the new entry's metadata and the cached belief's metadata are one
dict. That dict is then changed in place:

- `plane._apply_entry_verification(entry)` sets or pops `metadata["verification_failed"]`
  (core/stateplane.py:395-404; hosted planes run with verification on, runtime.py:621);
- on an accepted revision `AGMEngine.revise` pops `superseded_by` / `supersedes` / `previous_value`
  and writes `previous_value_sha256` and `reason_for_revision` (adaptive/agm_engine.py:494-501).

The polluted `previous_state` is then used as the "before" of the change:
- the UPDATE audit row's `before_value` (runtime.py `plane.audit.log(OpType.UPDATE, ...,
  before_value=previous_state, ...)`), which the hash chain then covers for good;
- the REVISE memory event's `before_value` (`_record_revision`, core/stateplane.py:3571-3592);
- the `next_state != previous_state` comparison that decides whether an audit row is written;
- on a rejected revision, the returned `entry_version(previous_state)`, which can then differ from
  the stored row's real version when the verification flag changed.

The improve audit reproduced the first on 085bb99: after commit + revise, the newest audit row's
`before_value.metadata` held `previous_value_sha256` and `reason_for_revision` while the stored row
before the edit had `{}`. The code at those lines is unchanged on 29ed56d.

Not affected: local `StatePlane.commit_with_agm_async` uses `previous_entry.to_dict()` (a fresh deep
copy, `asdict`). `ProjectRuntimeManager.confirm` (runtime.py:1183-1191) also builds entries from a
shallow copy, and `confirmed` shares its metadata with `previous_state`; but nothing between building
it and the audit log changes that metadata, `backend.save(confirmed)` (runtime.py:1186) included, so
the audit `before_value` (runtime.py:1194) is the stored row. It stays out of scope (named in the
release note as the same pattern, not a bug today); test 4 guards it.

## Approaches

1. **Deep-copy `previous_state` at the two places in `_revise_loaded` that build entries from it.**
   `previous_state` stays the exact dict that was version-checked, for the audit row, the event, the
   change comparison and the rejected-branch version. Two lines plus an import; no other behaviour
   changes. Overhead: one deep copy of one row's dict per revise.
2. **Make `MemoryEntry.from_dict` copy `metadata` (and `ccs_dimensions`).** Fixes the whole class,
   but it is the constructor every row load and every restore goes through, in both backends, and
   some code may rely on today's aliasing (the reserved-key strip deliberately returns the same object
   so versions do not change). Wider than the verified gap.
3. **Freeze the "before" once (e.g. `before = copy.deepcopy(previous_state)` at the top) and log
   that.** Fixes the audit row, but leaves `previous_state` polluted for the rejected-branch version,
   the change comparison and any later reader; every use site would have to be switched and kept
   switched.

## Choice: approach 1

It fixes every use of `previous_state` at the point where the aliasing is created, with the smallest
change, and keeps model and engine code (whose in-place writes are correct for an entry that owns its
metadata) untouched. Approach 2 is a separate, broader hardening question; approach 3 fixes one
symptom.

## Changes

- `src/bilinc/cloud/runtime.py`: `import copy`; in `_revise_loaded` replace `dict(previous_state)` at
  line 1252 (the entry that is changed in place) with `copy.deepcopy(previous_state)`, with a two-line
  comment saying why. Decided (gate round 1): line 1248 (the cached belief, which no code changes in
  place today) also gets `copy.deepcopy` as a one-line defensive copy so no live object shares
  `previous_state`'s metadata; no test is invented for it, and the release note says it is defensive.
- `CHANGELOG.md` `[Unreleased]` / `### Fixed`: one plain bullet; records written earlier are unchanged.
- No change to stored audit rows or events: the hash chain covers them; old rows stay as they are.

## Test plan (test first; `bilinc-test` only)

New tests in `tests/test_cloud_runtime_revise_before.py`, each parametrized over the SQLite and the
Postgres backend (throwaway schema on `BILINC_TEST_POSTGRES_DSN`, which `bilinc-test` sets):

1. Commit a key, then revise it twice (the second time the stored row already carries a
   `previous_value_sha256`). After each revise: the newest UPDATE audit row's `before_value` equals
   the stored row read just before the revise, and its `after_value` equals the stored row after;
   `previous_value_sha256` is in the stored row after, never in the before state. Red on 29ed56d.
2. Same scenario: the newest REVISE memory event's `before_hash` (the ledger stores only the hash,
   storage/postgres.py:334, 481 and the SQLite twin) equals the ledger's own hash function applied to
   the stored row read just before the revise.
3. Rejected revision under `ConflictStrategy.ENTRENCHMENT` (the default): write the row directly with
   `plane.backend.save(...)` (skipping verification) with metadata `{"verification_failed": ["x"]}`, a
   value that passes verification and importance 0.9, and set its entrenchment to 0.9; revise with
   importance 0.3 so the revision is rejected: the returned `entry_version` equals the version of the
   stored row, which is unchanged. Red on 29ed56d on both backends (the verification pop empties the
   shared metadata, so the returned version is that of a row that was never stored).
4. Confirm path unchanged: a `confirm` after the fix still writes the same audit `before_value` as the
   stored row (guards the out-of-scope claim).

Mutation checks before the code gate: revert the line-1252 deep copy (tests 1-3 must fail); the
line-1248 copy is defensive and not mutation-tested; compare `before_value` with a fresh
`to_dict()` taken after the revise instead of before (test must be meaningful, not tautological).
Full gate: `bilinc-test -q -m public_source`, `-m internal_runtime` (Postgres runs), `ruff check`.
