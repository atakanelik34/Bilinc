# A8b: hosted planes are never evicted

## Problem
`ProjectRuntimeManager._planes` (cloud/runtime.py:447) gets one `StatePlane` per project on first use (`get_plane`,
runtime.py:476-523) and keeps it until the process ends; the only removal is `_evict_plane` on project purge
(runtime.py:1241) and `close()` (runtime.py:1551). Each plane holds a storage backend (on Postgres a connection pool plus,
for the audit trail, a separate connection), the AGM belief state loaded from every entry of the project
(runtime.py:513-515) and the knowledge graph. In a long-running process the number of loaded planes only grows with the
number of distinct projects ever touched, and on Postgres each one keeps database connections open, which is
what a shared database's connection limit pays for. No measurement of that cost is claimed here.

How the sites were found: `grep -rn "_planes\|get_plane" src/bilinc` (only runtime.py touches `_planes`); `get_plane` is
called from the eleven public per-project methods (commit, recall, history, list_memories, revise, confirm, forget,
create_snapshot, list_snapshots, diff, rollback_preview, rollback_execute) and from `purge_project`'s eviction.

## What is lost when a plane is dropped (and why that is safe)
A plane is rebuilt on the next call by `get_plane` from storage: entries, claims, audit chain and events are durable; the AGM
belief state is reloaded from the entries (runtime.py:513-515); `_belief_is_stale` (runtime.py:406) already re-checks a cached
belief against persisted state. Process-memory-only state (the AGM operation log and counters, working-memory slots, caches)
is already lost on every process restart, so nothing durable may depend on it; it also resets on eviction. The per-project
mutation locks (`_mutation_locks`, tiny) are deliberately kept, so a mutation in flight and one that starts after an eviction
can never hold two different locks.

## Approaches
1. Leave it and document "restart periodically". No code, but connection and memory use then depend on an external habit.
2. Cap only (LRU, N planes). Bounds growth, but a cap sized for a busy hour keeps idle projects' connections open all night, and
   a cap that is too small thrashes.
3. Idle timeout plus an optional cap, evicting only planes with no operation in flight, swept opportunistically at call
   time. A background reaper task was rejected: one more task with its own lifecycle, and idle resources only matter when
   other projects are active, which is exactly when calls arrive.

Chosen: 3.

## Design
- Settings read when the manager is built: `BILINC_CLOUD_PLANE_IDLE_SECONDS` (default 1800; 0 or negative = never evict by
  idleness) and `BILINC_CLOUD_PLANE_MAX` (default 0 = no cap; with a cap, the least recently used planes without an operation in
  flight are evicted when the count exceeds it; if all are in flight the count may exceed the cap for the moment). Invalid values
  fall back to the default with a log line that names the variable, not the value.
- Leases: a decorator `_leased_plane` on the eleven public per-project methods increments `_inflight[project]` and sets
  `_last_used[project]` at entry, before the first `await`, and decrements in `finally` (setting `_last_used` again). Because
  an asyncio task runs without interruption between awaits, the sweeper's "in flight is zero, so pop the plane" check and
  the pop are one atomic step; a call arriving afterwards builds a fresh plane through `get_plane`.
- Sweep: at the start of each leased call, `_evict_idle()` collects planes whose `_inflight == 0` and (`now - _last_used >= idle`
  or over the cap, oldest first), pops them from `_planes` synchronously, then closes them: `forget_tenant` on the indexer, close
  of backend and audit, as `_evict_plane` already does. Close errors and a 10 second close timeout are logged
  (exception type only) and never fail the call that triggered the sweep.
- The embedding indexer iterates a snapshot of `_planes`; a plane evicted while it is being indexed can make that one pass fail,
  which `run_once` already catches per tenant (embeddings/hosted.py:131-134) and logs; the next pass uses the fresh plane.
- `purge_project` and `close()` keep their own handling; `_clock` (default `time.monotonic`) is an attribute so tests control it.
- Behaviour change to expect: the first request after an eviction pays the plane reload (cost grows with the project's entry
  count; not measured), and the in-memory operation log/counters of an evicted plane start empty. The owner can switch it off
  per deployment with `BILINC_CLOUD_PLANE_IDLE_SECONDS=0`.

## Test plan (tests first, `bilinc-test`; SQLite mode always, Postgres gated on `BILINC_TEST_POSTGRES_DSN`)
- Idle eviction: commit to project A, advance the fake clock past the idle time, call project B; A leaves `_planes`, its backend
  is closed, and a later recall on A returns the committed memory (reloaded from storage).
- In flight is never evicted: hold an operation on A open (backend call blocked on an event), advance the clock, call B; A is
  still loaded and the blocked operation completes normally; after it finishes and the clock advances again A is evicted.
- A mutation in flight and a mutation started after an eviction of the same project still serialize (same lock object kept).
- Never: idle 0 keeps planes; cap: with cap 2 and three idle projects the least recently used is evicted, with all three in flight
  nothing is evicted; settings parse (garbage falls back to the default without crashing).
- Close failure: a backend whose close raises or hangs does not fail the triggering call and the plane is gone from `_planes`.
- The indexer's `forget_tenant` is called for an evicted Postgres plane (stub indexer).
- Churn stress: five projects, fake clock advancing by more than the idle time on every call, 40 concurrent mixed commits and
  recalls; every call succeeds and every committed key is readable at the end.
- Postgres (gated): after eviction the plane's pool and audit connection are closed, and a following recall reloads the data
  through the same tenant schema.
- Mutation check: removing the in-flight check makes the in-flight test fail; removing the cap logic fails the cap test;
  skipping the sweep fails the idle test.

## Release-chain impact
- PyPI package: none (`cloud/` is pruned from the wheel and sdist, `MANIFEST.in`). SDK, site, MCP registry: no change.
- Hosted runtime: changes; ships only with the next synchronized version and its redeploy. Two optional environment settings
  are introduced; the defaults turn idle eviction on at 30 minutes, which the owner may change at deploy time.
- Migration: none; rollback is a revert (or setting the idle seconds to 0).
- CHANGELOG `[Unreleased]` entry in neutral wording (no deploy internals).
