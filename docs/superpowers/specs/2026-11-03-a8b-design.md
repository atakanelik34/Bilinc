# A8b: hosted planes are never evicted

## Problem
`ProjectRuntimeManager._planes` (cloud/runtime.py:447) gets one `StatePlane` per project on first use (`get_plane`,
runtime.py:476-523) and keeps it until the process ends; the only removal is `_evict_plane` on project purge
(runtime.py:1241) and `close()` (runtime.py:1551). Each plane holds a storage backend (on Postgres a connection pool plus,
for the audit trail, a separate connection), the AGM belief state loaded from every entry of the project
(runtime.py:513-515) and the knowledge graph. In a long-running process the number of loaded planes only grows with the
number of distinct projects ever touched, and on Postgres each one keeps database connections open, which is
what a shared database's connection limit pays for. No measurement of that cost is claimed here.

How the sites were found: `grep -rn "_planes\|get_plane" src/bilinc` (only runtime.py touches `_planes`); `get_plane` is
called from eleven public per-project methods (commit, recall, history, list_memories, revise, confirm, forget,
create_snapshot, diff, rollback_preview, rollback_execute; runtime.py lines 594, 671, 708, 779, 874, 916, 1089, 1271, 1353, 1416,
1461). `list_snapshots` (runtime.py:1295) reads snapshot files and never loads a plane, so it gets no lease; `purge_project`
evicts the plane itself and stays unleased on purpose.

## What is lost when a plane is dropped (and why that is safe)
A plane is rebuilt on the next call by `get_plane` from storage: entries, claims, audit chain and events are durable; the AGM
belief state is reloaded from the entries (runtime.py:513-515); `_belief_is_stale` (runtime.py:406) already re-checks a cached
belief against persisted state. Process-memory-only state (the AGM operation log and counters, working-memory slots, caches, and the knowledge graph) is already
lost on every process restart, so nothing durable may depend on it; it also resets on eviction.
The knowledge graph deserves its own sentence: `init_knowledge_graph` (stateplane.py:3424-3448) builds it empty and only commits
fill it (stateplane.py:3555-3580); recall reads it for entity boosts (stateplane.py:2779-2811). A reloaded plane therefore ranks
like a freshly restarted process, not like a plane that has seen recent commits, so an eviction can change a project's recall
ranking slightly. Loading the graph from storage at plane load is the blocked item A3 (the entity boost hurt English recall in an
earlier trial), so this item does not change it. The per-project
mutation locks (`_mutation_locks`, tiny) are deliberately kept, so a mutation in flight and one that starts after an eviction
can never hold two different locks. That map still grows with the number of distinct projects and is never trimmed; this is
accepted (one small object per project) and means the item bounds planes and connections, not every per-project object.

## Approaches
1. Leave it and document "restart periodically". No code, but connection and memory use then depend on an external habit.
2. Cap only (LRU, N planes). Bounds growth, but a cap sized for a busy hour keeps idle projects' connections open all night
   (nothing reacts to idleness), and a cap that is too small thrashes.
3. Idle timeout (a small reaper task) plus an optional cap, evicting only planes with no operation in flight. A sweep that runs only
   when calls arrive was considered and rejected: a process with no calls would keep its planes and its database connections
   open indefinitely, and those count against a shared connection limit whether or not this process is busy.

Chosen: 3.

## Design
- Settings read when the manager is built: `BILINC_CLOUD_PLANE_IDLE_SECONDS` (default 0 = off: never evict by idleness, no reaper;
  a positive value is the idle time in seconds) and `BILINC_CLOUD_PLANE_MAX` (default 0 = no cap; with a cap, the least recently used planes without an
  operation in flight are evicted when the count exceeds it; if all are in flight the count may exceed the cap for the moment).
  Invalid values fall back to the default with a log line that names the variable, not the value.
  Both settings are off by default on purpose: switching eviction on makes the knowledge-graph reset above, and a plane reload
  whose cost is not measured, routine production events. That is the owner's call at deploy time, so the code ships the
  mechanism and the owner enables it.
- Leases: a decorator `_leased_plane` on the eleven methods above first normalizes the id with `normalize_project_id` (the key
  `_planes` and the evictor use; an invalid id raises `invalid_project_id` before any counter is touched), then increments
  `_inflight[normalized]` and sets `_last_used[normalized]` at entry and decrements in `finally` (setting `_last_used` again). It is the OUTERMOST decorator, outside
  `_serialized_project_mutation` (runtime.py:49-68): that wrapper awaits the project lock before the method runs, so only an outer
  lease is taken before the first `await`. An asyncio task runs without interruption between awaits, so the evictor's check "in
  flight is zero" and its pop of the plane are one atomic step; a call arriving afterwards builds a fresh plane via `get_plane`.
- Reaper: started lazily with the first plane (like the embedding indexer), cancelled and awaited in `close()`. Every
  `_reap_interval` seconds (`clamp(idle / 4, 5, 60)`, an attribute so tests set it) it runs `_evict_idle()`. The cap is enforced
  synchronously at plane creation in `get_plane`, after the new plane is registered, by the same code path.
- Eviction = pop synchronously, close off the request path. `_evict_idle()` pops the chosen planes from `_planes` in one step
  (no `await` between check and pop) and hands each to a tracked background task (`self._closing`, a set that removes finished
  tasks). No request waits for a close, so one tenant's call can never be stalled by another tenant's slow close.
- Closing one plane: `forget_tenant` on the indexer, then `close()` of backend and audit inside `asyncio.wait_for(..., 10)`.
  On timeout or error it force-closes: `pool.terminate()` on a Postgres backend (a plain `pool.close()` waits for connections
  still held, for example by an indexer pass) and closes the audit connection; the exception type is logged, never the message.
  `forget_tenant` is called once more after the close finished. The audit trail is closed on the event-loop thread by awaiting its own `close()`: the SQLite `AuditTrail` connection was opened on
  that thread with `check_same_thread=True` (audit.py:136), so closing it from a worker thread would raise `ProgrammingError`, and
  both audit closes are quick local operations (a file or a socket), accepted as not bounded by the timeout; only the backend
  close (which can wait on held connections) is bounded and terminated. Evicting a plane also deletes its `_inflight` and
  `_last_used` entries (its in-flight count is 0 then), so those maps do not grow.
- `close()` of the manager cancels the reaper, then awaits every pending closing task under one 10 second bound and terminates
  what is still pending, then closes the planes that remain with the SAME per-plane routine (indexer `forget_tenant`, backend,
  audit trail), so the shutdown path and the eviction path are one piece of code. Today `close()` closes only the backends
  (runtime.py:1551-1554) and leaves the audit connections to the garbage collector; this fixes that too.
- Missing bookkeeping: a plane without a `_last_used` entry counts as the oldest (0.0); the evictor still takes only planes whose
  in-flight count is zero.
- `purge_project` awaits the pending closing tasks of that project (closing tasks are tracked as task -> project id) under the same
  10 second bound, then terminates, before it removes the directory or drops the schema, so a delete never races a connection
  still being closed (on Postgres, a `DROP SCHEMA` could otherwise queue behind an indexer query on the old pool).
- The embedding indexer iterates a snapshot of `_planes`; a pass still running on an evicted backend may fail, which
  `run_once` catches per tenant and logs (embeddings/hosted.py:131-134), and may write `_failed`/`_passes` entries for that schema
  after the first `forget_tenant`; the second `forget_tenant` after the close clears them, and a leftover would only cost one
  extra embedding pass for the new plane (accepted).
- `purge_project` keeps its own eviction (and drops the same two entries); `_clock` (default `time.monotonic`) is an attribute so tests control it.
- Behaviour change to expect: the first request after an eviction pays the plane reload (cost grows with the project's entry
  count; not measured), and the in-memory operation log/counters of an evicted plane start empty. The owner can switch it off
  per deployment with `BILINC_CLOUD_PLANE_IDLE_SECONDS=0`.

## Test plan (tests first, `bilinc-test`; SQLite mode always, Postgres gated on `BILINC_TEST_POSTGRES_DSN`)
- Idle eviction (drives `_evict_idle()` with the fake clock): commit to project A, advance the clock past the idle time; A leaves
  `_planes`, its backend ends up closed (after the closing task is awaited), and a later recall on A returns the committed memory.
- In flight is never evicted: hold an operation on A open (backend call blocked on an event), advance the clock, run the
  evictor; A is still loaded and the operation completes normally; afterwards, with the clock advanced again, A is evicted. Same
  for a mutation holding the project lock.
- A mutation in flight and one started after an eviction of the same project still serialize (the lock object is kept).
- The lease normalizes: an operation in flight on an upper-case UUID is not evicted; an invalid id raises `invalid_project_id` and
  leaves no `_inflight` or `_last_used` entry. After an eviction both maps hold no entry for the project.
- Audit chain across an eviction (SQLite always, Postgres gated): commit, evict, commit again, then forget; the audit chain
  verifies end to end and the first new entry's `prev_root` equals the last `root_hash` from before the eviction. Sanity check
  of the test itself: with the rebuilt audit trail forced to start from the genesis hash the test fails.
- Knowledge graph: the test records that a rebuilt plane starts with an empty graph (the documented, restart-equivalent state).
- Never: idle 0 keeps planes and starts no reaper; cap: with cap 2 and three idle projects the least recently used is evicted,
  with all in flight nothing is evicted; garbage settings fall back to the defaults without crashing.
- Slow close does not stall a request: a plane whose backend close hangs forever is evicted while another project's call is
  awaited; that call returns without waiting for the close; the hanging plane ends up terminated (the stub's terminate is
  called), and `close()` of the manager returns within its bound with nothing left pending.
- Close errors: a close that raises does not fail anything and the plane is gone from `_planes`.
- Per backend: in SQLite mode, after an eviction the evicted plane's `audit.conn` is closed (or `None`) and nothing was logged at
  error level (this is the check the previous design missed); in gated Postgres mode the audit connection and the pool are closed.
  Sanity check of the test itself: closing the SQLite audit through `asyncio.to_thread` makes it fail.
- Purge waits: evict a plane whose backend close hangs, run `purge_project` for it; purge waits for the bound or the termination
  and then succeeds (directory removed / schema dropped).
- Manager `close()` closes the audit trail of the planes that remain, not only their backends.
- A plane with no `_last_used` entry is treated as the oldest.
- Reaper lifecycle: with a tiny `_reap_interval` the task evicts an idle plane without any call, and `close()` cancels it.
- The indexer's `forget_tenant` is called for an evicted Postgres plane, before and after the close (stub indexer).
- Churn stress: five projects, fake clock advancing by more than the idle time on every call, evictor running between calls, 40
  concurrent mixed commits and recalls; every call succeeds and every committed key is readable at the end.
- Postgres (gated): after eviction the plane's pool and audit connection are closed, and a following recall reloads the data
  through the same tenant schema.
- Mutation check: removing the in-flight check fails the in-flight test; removing the cap logic fails the cap test; skipping the
  eviction fails the idle test; closing inline instead of in the background fails the slow-close test.

## Release-chain impact
- PyPI package: none (`cloud/` is pruned from the wheel and sdist, `MANIFEST.in`). SDK, site, MCP registry: no change.
- Hosted runtime: changes; ships only with the next synchronized version and its redeploy. Two optional environment settings
  are introduced, both off by default, so a redeploy changes nothing until the owner sets `BILINC_CLOUD_PLANE_IDLE_SECONDS`
  (and optionally `BILINC_CLOUD_PLANE_MAX`). They are documented in the runtime module docstring and the CHANGELOG line; there is
  no public documentation for them. Enabling them in production is an owner step (see the knowledge-graph and reload notes).
- Migration: none; rollback is a revert (or setting the idle seconds to 0).
- CHANGELOG `[Unreleased]` entry in neutral wording (no deploy internals).
