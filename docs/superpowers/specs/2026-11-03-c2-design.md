# C2: the legacy `vec_bilinc` vector level is dead code that can still read stale vectors

## Problem
`HybridSearch.hybrid_search` has a "Level 2: Vector" step (`core/vector_search.py:517-560`; `search_with_reranking`, `:576`, goes through it, and `StatePlane` calls both, `core/stateplane.py:2378, 2561`): it asks a local Ollama server for an embedding of the query (`get_embedding`, `:45`, an HTTP call to `http://localhost:11434` with a 10 s timeout) and, if one comes back, searches the `vec_bilinc` table of the SQLite file (`VectorStore.search`, `:211-228`) and fuses the hits into the ranking.

- **Nothing writes the table any more.** The only writer, `VectorStore.index_entry` (`:197-208`), has no caller in `src/` or `tests/`. Semantic vectors now live in other tables (`embeddings/store.py`, via the local embedding daemon).
- **The table can still hold rows.** The owner's local database holds 315 vectors at rowids 1-316 from older versions (Vault Local-Audit, 2026-10-22). They are embeddings of memories that were later forgotten or rewritten, and a forget or purge never deletes from `vec_bilinc` (`vector_search.py:185-233` is the only code that touches it). That is a privacy residue: an embedding is derived from the removed text.
- **A stale vector can match a different memory.** The search filters hits by `rowid` against the candidate memories (`allowed_rowids`). A new memory that reuses one of those old rowids would receive the old vector's score. It needs a running Ollama to happen, which is why nobody saw it; it is still wrong.
- **Every search makes a network attempt.** `get_embedding` runs on each hybrid search, and fails fast only because nothing listens on that port on most machines. It also sends the query text to whatever does.
- This path exists only for local SQLite: `StatePlane._get_hybrid_search` builds `HybridSearch` solely from `_sqlite_connection()` (`core/stateplane.py:3009-3018`), and the Postgres backend has no such connection, so Cloud never used the table and the local-to-Cloud behaviour does not change.
- `StatePlane._get_hybrid_search` (`core/stateplane.py:3023-3038`) creates the table (`VectorStore._ensure_schema` runs `CREATE VIRTUAL TABLE IF NOT EXISTS vec_bilinc`) in every SQLite database that has the `sqlite-vec` extension.

## Approaches
1. **Remove the legacy vector level, and give the owner an opt-in way to drop the old table (chosen).**
   - Code: delete `get_embedding`, `serialize_float32`, the "Level 2: Vector" step and its fusion term, and the `VectorStore` class (table creation, `is_available`, `index_entry`, `search`, `count`). `HybridSearch.__init__` drops its `vector_store` argument entirely, and the callers are updated (`StatePlane._get_hybrid_search` and the 11 construction sites in `tests/test_vector_search.py` and `tests/test_turkish_search.py`): a shim that accepts and ignores the argument would protect nobody, since `core` is not part of the wheel or sdist and the only users are inside this repository.
   - `core/__init__.py` exposes `VectorStore` in `__all__` (line 16) and in the lazy `_IMPORTS` table (line 50); both entries are removed, so `bilinc.core` still imports and `from bilinc.core import *` still works.
   - **The `sqlite-vec` extension is no longer loaded.** `SQLiteBackend` runs `enable_load_extension(True)` and loads `sqlite_vec` on every connection (`storage/sqlite.py:101-107`), and `vec0` is used nowhere else in the repository. After this change that block is dead code, and it leaves extension loading enabled on every connection, which lets SQL call `load_extension()`: a needless opening in a product whose point is privacy. The block is removed. A database that still has an old `vec_bilinc` virtual table opens and works without the module: opening, writes, forget and purge, and the FTS rebuild do not touch it (a test shows it). The drop script loads `sqlite-vec` itself, only when asked to drop.
   - Ranking does not change in practice: with the table empty or unreachable the vector hits were always empty, so only keyword scores were fused, with the same keyword weight; the fusion keeps its keyword weights as they are.
   - Existing databases keep a `vec_bilinc` table that nothing reads or writes. `scripts/drop_legacy_vec_table.py` removes it, owner-run: read-only count by default (it counts the table's rowid shadow table, which needs no extension); `--execute` needs `--backup-dir`, takes the write lock first, copies the database with SQLite's backup API (mode 0600), verifies the copy, loads `sqlite-vec` (it refuses to run when the extension is missing, because a virtual table cannot be dropped without its module), runs `DROP TABLE vec_bilinc` in one transaction with `secure_delete` on, then truncates the write-ahead log, as the scrub script of backlog item PREV-VAL does.
2. **Keep the vector level and delete from `vec_bilinc` on forget and purge.** Rejected: nothing writes the table, so a delete path would guard rows that cannot be created again; the rows that exist are keyed by old rowids that no longer map to the removed memories, so a delete by the memory's rowid would not find them. It keeps the dead code and the network attempt.
3. **Only stop creating the table and drop the writer.** Rejected: leaves `get_embedding` and the stale-vector read path in place, and the existing rows stay.

## Test plan (tests first, small commits)
1. **No network attempt.** `hybrid_search` and `search_with_reranking` make no HTTP request: urllib's `urlopen` is patched to fail the test if called, and a search still returns the keyword results (SQLite; the existing hybrid tests in `tests/test_vector_search.py` and `tests/test_turkish_search.py` stay green with the `vector_store` argument removed from their construction calls).
2. **No stale vectors.** A database that has a `vec_bilinc` table with a row at the rowid of a new memory (a plain table of that name stands in for the virtual one, so the test needs no extension) returns the same ranking as one without: the table is not read.
3. **No table is created, no extension is loaded.** A new database opened through `StatePlane` has no `vec_bilinc` table, and the connection refuses `load_extension()` (extension loading is off).
3b. **A database with an old `vec_bilinc` still works without the module.** A database whose `sqlite_master` has a `vec_bilinc` entry (a stand-in virtual-table row where `sqlite-vec` is not installed, the real one where it is) opens through `SQLiteBackend` and `StatePlane`, takes writes, forgets and purges a key, and rebuilds its full-text index, without loading any module.
3c. **Imports.** In the runtime package (`internal_runtime`), `import bilinc.core` and `from bilinc.core import *` run without error and `VectorStore` is no longer exposed.
4. **Ranking unchanged.** For a set of queries over a fixed set of memories, the ranked keys and their order before and after the change are the same (the expected order is recorded from `origin/main` in the test as data).
5. **The script.** Read-only count: the file is byte-identical afterwards and the row count matches; `--execute` without `--backup-dir` refuses; with it, a backup (mode 0600) opens with the same table, no `sqlite_master` object named `vec_bilinc%` remains (the shadow tables `vec_bilinc_rowids`, `_chunks`, `_info`, `_vector_chunks00` and the like hold the vector bytes), every table outside that family and its rows are unchanged, the seeded vector bytes are not in the database file or in its `-wal`, and a second run finds nothing. A busy database (another connection holds the write lock) is left unchanged with a non-zero exit. When `sqlite-vec` cannot be loaded `--execute` refuses before touching anything (the module is faked as missing where it is installed). If `sqlite-vec` is not installed in the test environment, the drop test is skipped and the other cases run on a plain stand-in table for the count and refusal paths.
5b. **Postgres.** The Postgres tests only act as a regression check: the Cloud path never used this table, so nothing in them is expected to change.
6. Run through `bilinc-test` only: `-q -m public_source`, `-q -m internal_runtime`, the Postgres tests, and `.venv/bin/ruff check`.

## Rollback and who runs what
- Code: revert the commit. No schema change: the code only stops creating, reading and writing a table.
- The drop removes a table for good. The way back is the count first, the script's 0600 backup (it holds the vectors being removed: keep it or destroy it once the result is checked) and the owner's own backups.
- **Running the script on the owner's `~/bilinc.db` is an owner step** (backlog LOCAL-REPAIR): stop the Bilinc processes first. The worker ships code and tests only and touches no real database.

## Release-chain impact
- **Where the code ships.** `core` and `storage` are pruned from the PyPI wheel and sdist (`MANIFEST.in`, `pyproject.toml` `packages`, `docs/repository-contract.md:13`): this ships in the internal source and the local stdio adapter. `scripts/` is not part of the wheel or sdist either (nothing includes it; the build-time check in `tests/test_cloud_only_package.py` would show it), so the script runs from a repository checkout.
- **Version.** Runtime-only deployment or inside a synchronized version is the owner's decision; if a version moves, the whole chain moves (`pyproject.toml`, `bilinc.__version__`, `server.json` and the MCP registry entry, runtime image, site version display).
- **SDK behaviour, site code, MCP tool list:** unchanged. No API, tool schema or response field changes.
- **Migration:** none automatic; the table drop is an owner-run script.
- **Public text:** nothing public mentions this table or Ollama.
- **CHANGELOG:** one line under Fixed and one under Added. Other ready branches also add a top `[Unreleased]` section, so the merge needs a trivial conflict resolution.
