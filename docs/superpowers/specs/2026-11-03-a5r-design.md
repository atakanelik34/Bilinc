# A5r: TTL read points must agree with the write rule

## Problem
A TTL write sets `ttl` and `invalid_at = write_time + ttl` (stateplane.py `_commit_with_ttl`, ~3499-3501) and keeps
`created_at` fixed on upsert (correct, and not to be changed). One read point honours that rule
(`_is_visible`, ~1946-1954: `created_at + ttl` counts only when `invalid_at is None`). Four others
measure from `created_at` regardless of `invalid_at`, so a key first written long ago and re-committed with a fresh TTL
is treated as expired / stale although its `invalid_at` is in the future:

| Read point | Effect today |
|---|---|
| as-of filter (~1855-1857) | row dropped from as-of recall at times before its real expiry |
| ranking penalty (~2697-2698) | -0.04 on a live row |
| quality flags (~1289-1292) | "expired" flag on a live row |
| `MemoryEntry.is_stale` (models.py:171-176) | live row reported stale (verification, forgetting engine, `BeliefState` listings) |

Both modes are affected (local SQLite and hosted Postgres share this code).

## Approaches
1. Patch each of the four sites with the same `invalid_at is None` guard. Small, but five copies of one rule drift again.
2. One shared predicate `ttl_expired(created_at, ttl, invalid_at, now)` in `core/models.py`, used by all five sites
   (including `_is_visible`). Rule: if `invalid_at` is set it alone decides; otherwise `created_at + ttl <= now`.
3. Rewrite `invalid_at` on read or move `created_at` on upsert. Rejected: read paths must not write, and moving
   `created_at` breaks history order and ranking recency.

Chosen: 2. Behaviour change is limited to rows where `invalid_at` is set and in the future while `created_at + ttl` is past;
rows with only `ttl` (legacy, no `invalid_at`) keep the current behaviour. Rows with `invalid_at` in the past stay expired
through the existing `invalid_at` checks. The quality-flag site keeps its `invalid_at` branch and skips the TTL branch when
`invalid_at` is set (also removes a duplicate "expired" flag). Value parsing stays tolerant: unparsable values behave as today
at each site (flag site: "stale_possible"; others: treated as absent).

## Test plan (tests first, `bilinc-test`)
For each of the five sites, a row with `created_at` far in the past, `ttl` small, `invalid_at` in the future:
must be live (visible as-of at a time before `invalid_at`, no -0.04, no "expired" flag, `is_stale()` false, apart from strength).
Controls that must stay as is: invalid_at in the past -> expired everywhere; ttl only (no invalid_at) past -> expired;
re-commit via the real `commit` path with a fresh TTL on an old key (created_at unchanged, invalid_at moved) -> live at the
five sites. Unit tests for the predicate incl. string/None/garbage values. Mutation check: reverting the guard at each site
must make exactly that site's test fail. Run in SQLite mode and through the hosted runtime test on Postgres.

## Release-chain impact
Source-internal change (core/models, core/stateplane); not in the public wheel path beyond `core/models.py` behaviour of
`is_stale`; no migration, no data change, no schema change. Version is the owner's decision. CHANGELOG `[Unreleased]` entry.
