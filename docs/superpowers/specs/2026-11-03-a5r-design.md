# A5r: TTL read points must agree with the write rule

## Problem
A TTL write sets `ttl` and `invalid_at = write_time + ttl` (stateplane.py `_commit_with_ttl`, ~3499-3501) and keeps
`created_at` fixed on upsert (correct on both backends: postgres.py:761-782, sqlite.py:388-398; not to be changed).
One read point already honours the rule (`_is_visible`, ~1946-1954: `created_at + ttl` counts only when `invalid_at is None`).
Six others measure from `created_at` regardless of `invalid_at`, so a key first written long ago and re-committed with a
fresh TTL is treated as expired or stale although its `invalid_at` lies in the future.

How the list was found: `grep -rn "\.ttl\b\|\"ttl\"" src/bilinc` over the whole package (excluding writers and serializers:
postgres.py:772/787, sqlite.py:406, salience.py:80, cognitive_workspace.py:251, stateplane.py:1207/1257/3500 only store or
copy the value). Every remaining reader is below.

| # | Read point | Effect today |
|---|---|---|
| 1 | stateplane.py as-of filter (~1855-1857) | row dropped from as-of recall before its real expiry |
| 2 | stateplane.py ranking penalty (~2697-2698) | -0.04 on a live row |
| 3 | stateplane.py quality flags (~1289-1292) | "expired" flag on a live row |
| 4 | core/models.py `MemoryEntry.is_stale` (171-176) | live row reported stale; feeds `BeliefState.active_beliefs` (202), `verification.py:136` and `adaptive/forgetting_engine.py:187` |
| 5 | core/verification.py `_check_staleness` (188) | verdict STALE "TTL expired" on a live row (separate from the `is_stale` call at 136) |
| 6 | core/graph_doctor.py `_entry_status` (252-253) | `ttl_expired` reason, row marked not active |
| (ref) | stateplane.py `_is_visible` (1946-1954) | already correct; moves onto the shared predicate with no behaviour change |

Both modes are affected (local SQLite and hosted Postgres share this code).

## Approaches
1. Patch each site with the same `invalid_at is None` guard. Small, but seven copies of one rule drift again.
2. One shared predicate in `core/models.py`, used by all seven sites (six fixed + `_is_visible`).
3. Rewrite `invalid_at` on read or move `created_at` on upsert. Rejected: read paths must not write, and moving
   `created_at` breaks history order and ranking recency.

Chosen: 2.

### Predicate contract
`ttl_expired(created_at, ttl, invalid_at, now) -> bool`, pure, takes values already parsed to `float | None` by each
site's own existing parser (as-of filter: `parse_temporal_timestamp`; stateplane ranking/visibility: `_timestamp`;
graph_doctor: `_coerce_timestamp`; models/verification: raw floats as today). The predicate does no parsing, so each
site's tolerance for odd values is unchanged. Rule: if `invalid_at is not None` the TTL clause never fires (invalid_at alone
decides, through each site's existing `invalid_at` check); otherwise true iff `created_at is not None and ttl is not None
and created_at + ttl <= now`.

Comparison: the predicate uses `<=` and `is not None`, like the stateplane sites. Boundary differences that remain per site
and are NOT changed by this item: `is_stale` and `verification.py` keep their existing strict `>` on their own
`invalid_at` checks and on the age/TTL comparison (they call the predicate with `now - epsilon`-free semantics:
`ttl_expired` is evaluated as `created_at + ttl < now` there via a `strict` keyword, default False). Truthiness
(`if self.ttl`) at those two sites is kept as today (ttl 0 or None = no TTL); the predicate itself treats `ttl=0` as a TTL
of zero seconds like the stateplane sites. A boundary test pins both behaviours.

Flag site (#3): keeps its `invalid_at` branch; the TTL branch is skipped when `invalid_at` is set (also removes the
duplicate "expired" flag). Unparsable `ttl` still yields "stale_possible" as today.

Rows with only `ttl` (legacy, no `invalid_at`) keep the current behaviour everywhere. Rows with `invalid_at` in the past stay
expired through the existing `invalid_at` checks.

## Test plan (tests first, `bilinc-test`)
- Predicate unit tests: both set, invalid_at None, ttl None, created_at None, ttl 0, `now == created_at + ttl` boundary with and
  without `strict`.
- For each of the six sites: live-row test (`created_at` far past, small `ttl`, `invalid_at` future) and control tests
  (invalid_at past -> expired; ttl only and past -> expired). Includes a forgetting-engine test: a live re-committed TTL row is
  not treated as stale; and a `BeliefState.active_beliefs` test.
- Mutation check: removing the predicate use at each of the six sites must fail exactly that site's test.
- End to end on both backends, same scenario: write key, backdate `created_at`, re-commit with a fresh TTL through the real
  commit path, reload, assert `created_at` unchanged and `invalid_at` moved, assert recall visibility, no penalty, no
  "expired" flag, `is_stale()` false, verification not STALE, graph_doctor row active. SQLite: runs everywhere; Postgres: a test
  gated on `BILINC_TEST_POSTGRES_DSN` going through the hosted runtime and `PostgresBackend.load`.

## Release-chain impact
- PyPI package: changes (core/models.py, core/stateplane.py, core/verification.py, core/graph_doctor.py).
- Hosted runtime: changes (same modules); Cloud only gets the fix after a runtime redeploy of the same version.
- SDK client surface: no API change. Site: no change. MCP registry: version bump only, as part of the one release.
- Migration: none; rollback is reverting the code. No data change, no schema change.
- Ships only as part of one synchronized version everywhere; the version number is the owner's decision.
- Downstream behaviour change: re-committed TTL rows no longer count as stale in `BeliefState.active_beliefs`, the forgetting
  engine and verification.
- CHANGELOG `[Unreleased]` entry.
