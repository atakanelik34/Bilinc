# A8d: the audit root hash the rollback check compares against is a process-local cache

Follow-up of A8a (the chain lock stops forks; this is the other half of "a second writer"). Checked against origin/main 5578d27.

## Problem
Each audit trail keeps `_root_hash`, loaded at init and set after this process's own `log()` (audit.py:162, :213;
postgres_audit_sync.py:73, :116; postgres_audit.py:52, :91). `get_root_hash()` returns that cache. The hosted runtime's
`state_version(plane)` (runtime.py:172-176) is built on it and is used for the rollback confirmation binding:

- `rollback_preview` returns `current_root_hash = state_version(plane)` (runtime.py:1430), which the control plane binds its
  confirmation token to.
- `rollback_execute` refuses with `state_changed_since_preview` when `state_version(plane) != expected_current_root`
  (runtime.py:1465-1467), so an execute after the project moved on cannot discard newer state.
- `diff` against current state reports `to_root = state_version(plane)` (runtime.py:1355).

If another process wrote to the same project after this process's last write or init, the cache is stale: the preview can
return an old head, and the execute check compares a stale value with a stale value and passes, which is exactly the case it exists to
refuse. The cache is only right while this process is the only writer (today's one-worker design, runtime.py:49-68).

Not affected, and left alone: values returned right after this process's own write (`state_version` in commit/revise/forget
responses is the root that write produced, which is what a client wants), health (`health.py:128`), snapshot payloads
(`stateplane.py:3263, 3399`, informational).

## Approaches
1. Document "single writer". Leaves the one safety check that exists for destructive restores correct only by convention.
2. Make `get_root_hash()` itself read the database. Fixes every caller, but adds a query to every response and to health
   checks, and changes a method many callers treat as free.
3. Add a refresh that reads the head from the database, and use it only where the value is compared or bound
   (preview, execute check, diff-to-current). Cost: one indexed `ORDER BY id DESC LIMIT 1` on three rare operations.

Chosen: 3.

## Design
- `refresh_root_hash()` on the three audit trails: reads `SELECT root_hash FROM audit_log ORDER BY id DESC LIMIT 1`,
  stores it in `_root_hash` (so `get_root_hash()` is correct again afterwards), returns it (genesis hash `"0"*64` for an empty log).
  SQLite `AuditTrail` and `SyncPostgresAuditTrail` are synchronous like their `log()`; the async twin `PostgresAuditTrail` gets an
  `async` method. `get_root_hash()` stays a cache read.
- `fresh_state_version(plane)` in runtime.py next to `state_version`: `None` when audit is off, else
  `plane.audit.refresh_root_hash()`. Used in `rollback_preview`, the `rollback_execute` check, and the diff-to-current `to_root`.
  Everything else keeps `state_version`.
- Honest limit: the check and the restore are still two steps. A write landing between them is not caught (closing that needs the
  A8a chain lock held across the restore, a separate design). This item removes the arbitrary staleness; it does not make
  multi-writer use supported, and no text says it does.

## Test plan (tests first, `bilinc-test`; SQLite always, Postgres gated on `BILINC_TEST_POSTGRES_DSN`)
- Trail level, two writers on one store (two `AuditTrail` instances on one SQLite file; two `SyncPostgresAuditTrail` instances on
  one schema; one async twin pair on `public`): B logs; A's `get_root_hash()` is stale (documents the cache), A's
  `refresh_root_hash()` returns B's head and `get_root_hash()` then agrees; empty log returns the genesis hash.
- Runtime level, two `ProjectRuntimeManager` instances over one base directory (SQLite) and over one project (Postgres), standing
  in for two workers: A commits; A previews a rollback (token root X); B commits; A's preview now reports B's head, not X; an
  execute with the old expected root raises `state_changed_since_preview` and leaves the data untouched; an execute with the fresh
  root succeeds. Same for `diff` to current state. On origin/main the stale-root execute passes silently (red first).
- Single-writer behaviour unchanged: the existing rollback, preview and diff tests stay green; commit responses still carry the
  root their own write produced.
- Mutation check: using `state_version` instead of `fresh_state_version` at each of the three sites fails its test.

## Release-chain impact
- PyPI package: none (`core/` and `cloud/` are pruned from the wheel and sdist, `MANIFEST.in`). SDK, site, MCP registry: no change.
- Hosted runtime: changes; ships with the next synchronized version and its redeploy. Migration: none; rollback is a revert.
- Cost: one extra indexed query per rollback preview, rollback execute and diff-to-current (no measurement claimed).
- CHANGELOG `[Unreleased]` entry in neutral wording.
